# Surface contract: Telegram transport and CLI

## Boundary, consumers, and ownership

`TelegramTransportAdapter` in `src/telegram-transport.ts` implements the generic transport port. It owns Telegram parsing, sender/chat authorization, per-private-chat session selection and persistence, safe result/event presentation, long-polling lifecycle, and a token-derived polling lock. `src/cli.ts` validates configuration and composes one adapter with `ApplicationRuntime`; core and Pi RPC do not import Telegram code. Generic request/result/event guarantees are defined by [transport adapter](transport-adapter.md).

## Configuration and authorization

- Runtime startup loads an optional `.env` from the process current working directory before validating configuration. Process-environment values take precedence, file values are parsed as Node dotenv syntax (never executed as shell), and read errors are reported without exposing contents. See [CLI configuration](cli-configuration.md).
- `HARNESSD_TELEGRAM_BOT_TOKEN` and a nonempty comma-separated `HARNESSD_TELEGRAM_ALLOWED_USER_IDS` are required. IDs must be positive safe integers. `HARNESSD_PI_EXECUTABLE` defaults to `pi`; `HARNESSD_STATE_DIR` uses the core's standard resolution; `HARNESSD_HOME` optionally selects the initial per-chat directory and `/new` default; it defaults to `/` and is not a filesystem boundary. `harnessd --help` reports usage without requiring or loading configuration.
- `HARNESSD_EXECUTION_MODE` defaults to `direct` (trusted; `cwd` is not a sandbox). The CLI accepts only `direct` or `isolated`; because it registers no isolation provider, an isolated request fails safely before transport startup. Invalid values are rejected before configuration-driven transport construction.
- Every Telegram update, including callback queries, passes middleware before handlers: the sender must exist, have a positive safe numeric ID in the allowlist, and the chat must be `private`. Unauthorized/missing/malformed senders and groups/channels receive no reply, session data, or core dispatch.
- Allowlisted operators share access to all local sessions. The bot token is not logged or passed to Pi; child environment behavior remains the process-provider contract. Direct Pi is trusted local execution with the supervisor user's OS permissions; `cwd` is not a sandbox.

## Commands and session routing

- Supported commands: `/start`, `/help`, `/menu`, `/rename [sessionId] <name|--clear>`, `/sessions`, `/new [cwd]`, `/ls [path]`, `/cd [path]`, `/send <path>`, `/use [sessionId]`, `/resume [sessionId]`, `/inspect [sessionId]`, `/status`, `/model [provider/modelId [effort]]`, `/effort [level]`, `/reload`, `/stop [sessionId]`, `/delete <sessionId>`, and `/cancel <inputId>`. `/start` sends a Russian welcome with one-time workflow buttons bound to the authorized chat, sender, and exact welcome message; the buttons open or refresh the actual panel/session view or start the naming flow. The welcome message is never adopted, persisted, or pinned as the panel. If `/use` has no ID, it confirms the remembered selection or explains how to choose one; missing-selection replies link to `/sessions` and `/menu`. The shared visibility-tagged catalog generates CLI help, Telegram `/help`, and Telegram's command menu. Registration is best-effort; failure emits a correlated redacted diagnostic but does not prevent polling or manual command handling. Plain text and media submit to the session selected by that private chat. A reply to a reliably correlated bot final-output or activity message routes directly to that source session even when another session is selected; it does not change selection or ask for a routing choice. After restart, a reply may route only from a message authored by this bot whose exact generated final-output footer and single SessionId code entity match a known session; named and unnamed multipart footers (including valid ` · i/N` suffixes) are recognized. User or other-bot lookalikes are unknown. An unknown reply source is never guessed: the operator must explicitly choose the current selected target or cancel. Correlation is volatile and bounded to the most recent 128 relevant bot messages per chat; it is not reply history and is lost on restart. Replies to active naming ForceReply prompts are handled as names; superseded, expired, and stale naming replies, including media and replies after restart, never submit to Pi. If a selected session is deliberately stopped, core resumes that exact saved Pi-native session before submitting only the new input once. After a graceful service restart, the transport restores each chat's saved selection without starting Pi at transport startup; the first new input triggers core's normal resume path. If Pi is already working, the Pi RPC harness submits the new input to Pi's native steering queue rather than rejecting it or holding a second harnessd queue. `/resume` does not change selection and never falls back to a new session; its success reply explicitly says selection is unchanged and states the ordinary-message target. It offers a Select callback only when the resumed session is not already selected. Lifecycle replies identify the operation outcome, selection effects, and next message target/action. `/model` and `/effort` list available/current controls for the selected live session; on a stopped session they explain that a running Pi is required and direct the operator to resume, then select as needed. Model IDs are selected by stable `provider/modelId`, never by display name.
- `/new` treats the entire remaining command text as one `cwd` path; paths with spaces work unquoted, and one matching pair of outer single or double quotes is stripped. Unmatched leading quotes receive a safe syntax hint. It performs no shell execution or expansion other than `~` and `~/...` to the operating-system user's home. Without a path, `/new` uses that chat's current directory, initially `HARNESSD_HOME` or `/`; explicit relative paths resolve from the same chat directory, and absolute paths are accepted. `~` expansion is independent of `HARNESSD_HOME`. Core canonicalizes and validates either path. `/use` inspects before selection, and a failed lookup leaves the existing selection unchanged. Selection changes from `/use`, `/new`, and `/menu` are persisted per authorized private chat; bare `/use` inspects and confirms that saved selection. Explicit stop clears the selected chat's saved choice, and successful deletion clears every chat selecting the deleted session. Missing-session and persistence failures are reported with actionable guidance. Inspect/stop default to the selected session; cancel requires a selected session and exact `InputId`. Successful `/stop` clears that chat's selection when it stopped the currently selected session. Slash and confirmed panel Stop replies provide a one-time Resume-and-select callback bound to the authorized chat, sender, message, and session; it rechecks that the session remains stopped before resuming, and selection persistence failures are reported as partial success.
- `/reload` takes no arguments and targets only the selected session for that private chat. It reloads Pi resources without changing selection or restarting a process, and reports the session name/full ID plus the actual current ordinary-message destination. Selection is revalidated at the dispatch boundary; a change before dispatch aborts safely, while completion remains bound to the original session. Busy, unsupported, unavailable, and unconfirmed outcomes use fixed safe guidance; no reload is automatically retried.
- `/ls [path]` lists immediate files and folders in the supplied or current chat directory, hides dotfiles by default, bounds output to 100 entries, and never reads file contents. `/cd [path]` changes only the current chat's volatile navigation directory; `/cd` without a path goes to the OS user's home. Relative paths use the chat directory and absolute paths, `..`, and symlinks can reach any directory accessible to the service OS user. `HARNESSD_HOME` only selects the initial directory; it is not a sandbox. `/cd` does not change the cwd of running sessions. `/send <path>` uploads a regular file from the selected session's canonical cwd to that authorized private chat only; relative paths resolve against the session cwd, paths outside it are rejected, and files over 20 MiB or non-regular files fail safely. The Pi `send_file` tool explicitly sends a regular workspace file (optionally with a caption) to authorized private chats currently selecting that session; it uses the same canonical-workspace, symlink, regular-file, and 20 MiB checks. Outer matching quotes may surround a path containing spaces.
- Session names are optional, shared metadata in the harnessd SQLite record, independent of Pi-native data and `cwd`. They are trimmed, single-line, nonempty when set, and limited to 64 Unicode code points; duplicates are allowed. `/rename [sessionId] <name>` targets the explicit ID or selected session, and `--clear` removes the name. `/sessions` shows a selected marker, name plus short ID (or short ID), lifecycle status, and compact cwd; `/inspect` retains `Name · #<full SessionId>` (or `#<full SessionId>`) and cwd while escaping HTML and abbreviating displayed cwd paths after 600 Unicode code points. `/delete` requires one explicit ID and removes only a stopped harnessd metadata row; it neither stops a live session nor deletes Pi-native files or its `cwd`. Its confirmation states that the harnessd record and received inbox attachments are deleted while workspace and Pi-native files remain. A non-stopped record returns guidance to `/stop` it first. Successful deletion clears volatile selections for that ID and removes its inbox; if filesystem cleanup fails, deletion remains successful and the transport reports cleanup as pending for a later sweep. `/status` reports the name when present, full `SessionId`, saved cwd/lifecycle, and live model, effort, aggregate usage, and estimated USD cost; missing live data is marked unavailable, cost is not provider billing, and optional plugin-only per-model/subagent details are excluded. A partially successful model change is reported without claiming rollback.

## Session panel, event presentation, and backpressure

- `/menu` creates or refreshes one pinned inline panel per authorized private chat. It explicitly distinguishes the selected session (plain-message destination), preview session, and exact new-session creation directory. Previous/next change preview only; **Выбрать** alone commits preview as the selected session. Preview controls for model, effort, stop, delete, and resume address that preview session, independent of selection. Session-list failure is reported and preserves current and persisted selection; only a successful list that authoritatively omits the selected ID may clear it. Session panels distinguish record existence, per-chat message selection, and persisted Pi lifecycle status (running, stopped, starting/recovering, or failed/stale); a running record may be stale after an unclean supervisor exit and is not proof that Pi is live. Running-status sessions offer Stop and live controls; stopped sessions offer Resume, combined Resume and select, and Delete; non-stopped sessions do not offer Delete. Model/effort panels require a running Pi. Failed/stale sessions offer only core-supported stop/inspection recovery, never reattachment or replacement. The panel shows live parent-session usage when available (`↑` input, `↓` output, `R` cache reads, `CH` cache-hit rate, estimated cost, and actual context occupancy from Pi RPC `contextUsage`). Missing or null values display as unavailable, never as zero; subagent metrics are not available through supported harness interfaces. Preview and folder navigation are volatile. The bot-token-scoped private state file stores panel message IDs and per-chat selected session IDs (never prompt bodies); version-1 panel files remain readable and are upgraded on the next write.
- Panel live status is scoped to each chat's preview, independently of its selected ordinary-message destination; only the explicit **Выбрать** action changes selection. It queries that preview for current lifecycle/live metrics and derives busy/idle from agent events, with reload/recovery activity shown while owned. On startup, a persisted running record is stale until queried; absent metrics or query failure are unavailable, and offline is shown only when a successful session listing confirms there are no sessions. Starting, recovering, stopped, failed/stale, live-unavailable, offline, idle, and busy remain distinct; records alone never prove Pi liveness. Agent start/settled and recovery/fatal events, plus relevant create/resume/stop/delete/reload/preview/menu actions, refresh only chats previewing the affected session; stale generations and preview changes prevent late queries from overwriting newer intent. Per-chat renders coalesce newest-wins and deduplicate identical text plus keyboard. Telegram edits are serialized, spaced by at least 500 ms, and a waiting render becomes dispatch-ready within 2 seconds; that bound excludes a strict single-flight call already in flight, which is not canceled or overlapped and retains its existing 5-second API deadline. Once it completes, the newest queued render follows subject to spacing. Terminal lifecycle and explicit user actions flush. The displayed local `Обновлено: HH:mm:ss` changes only when projected visible lifecycle/activity/live semantics change, not on duplicate events or identical polls. Shutdown invalidates pending work and awaits bounded in-flight refreshes. Transient edit failure marks the stored panel stale and offers explicit refresh without duplicate panel creation or retry; only a confirmed message-not-found edit permits replacement. A created replacement ID is saved even if keyboard publication fails, and failed publication intents are dropped; a later `/menu` targets that replacement.
- Inline panel routes include session list/details, folder navigation, new-session creation with an optional name, model/effort selection, and stop/delete actions with button-level confirmation. Folder navigation lists directories independently from `/ls`, shows at most 100 directories, reports that limit, and guides access to further paths with `/cd <путь>`; `/ls` retains its mixed file-and-directory listing bounded to 100 entries. The session list marks the selection and shows name or short ID, lifecycle, and compact cwd; details retain the full ID. The new-session panel shows the creation directory in a bounded display (an ellipsis marks truncation). Creation prompts preserve repeated whitespace and visibly escape control characters; if the exact path cannot fit in one Telegram message, it is sent in bounded consecutive path messages before a short ForceReply prompt. The cwd dispatched for creation remains the exact original path. Initial and reissued create/rename name prompts display the complete escaped cwd; when it cannot fit alongside prompt instructions in one Telegram message, the exact path is sent in bounded consecutive path messages before a short ForceReply prompt, without changing the dispatched cwd. Folder buttons carry short opaque, volatile tokens bound to the authorized chat, panel message/generation, parent directory, and exact displayed target path; they never resolve a fresh-list index. Rerendering or replacing panel context invalidates them, and stale taps do not navigate and offer panel refresh. Stop/delete confirmation tokens are one-time and volatile, bound to chat, panel message/generation, session, action, and expected lifecycle; cancel, panel rerender, use, success, and observed lifecycle changes invalidate them. Post-stop Resume-and-select callbacks are also one-time, volatile, and bound to chat, sender, the exact action message, session, and lifecycle epoch; stale, replayed, and cross-chat callbacks do not act. Resume-and-select retains its epoch reference through inspect, resume, and selection, rechecking invalidation before each consequential step; failure leaves selection unchanged and is not reported as success. Direct-message Resume-and-select and Resume Select callbacks do not replace or pin the direct action message as the panel; they refresh the chat's existing panel when one is stored. Direct Select callbacks are one-time and bound to the authorized chat, sender, session, and exact action message. Panel Resume feedback distinguishes when the resumed session is already the ordinary-message target from when it is not. Epoch state is retired when no pending confirmation or in-flight confirmation operation references the session; in-flight operations retain their invalidation epoch until completion. Before acting, confirmation rechecks the session lifecycle. Stale, replayed, canceled, or state-mismatched confirmations have no side effect and require fresh intent. Tokens are not persisted, so restart invalidates them. The same core operations and safety checks as slash commands apply. Unauthorized and non-private callbacks are rejected before core dispatch. Malformed session IDs and callbacks targeting a session absent from the transport's current in-memory session set are also rejected before dispatch; stale session buttons offer a `/menu` refresh. Name prompts use ForceReply and identify the exact session target and cwd. Each private chat has one active naming flow; a new flow explicitly supersedes the prior one. Invalid input or operation failure reissues the flow against the same target. Create prompts offer Create unnamed and Cancel inline buttons; rename prompts offer Cancel, while clearing a name remains a separate action. Prompt identity uses the complete, anchored generated ForceReply envelope, including its complete instructions and exact named or unnamed target identity, not a marker or short prefix; cwd presentation characters including Unicode line and paragraph separators remain matchable. Known correlated activity/final-output reply routes take precedence over prompt-envelope detection. Stale text/media replies matching current Russian envelopes or complete historical English envelopes remain recognizable and are rejected after restart without persisted prompt state. After an explicit one-time cross-session reply-choice callback, the retained incoming media is dispatched to the confirmed source/selected destination without reclassifying its original reply; download begins only after confirmation. If the source already equals the selected session, only the selected-destination choice is shown. A confirmed-current route snapshots that selection and revalidates it under the inbox lock after inspection immediately before saving and again immediately before dispatch; if selection changes before saving, nothing is written or submitted, and if it changes after saving the newly saved file is safely removed under the lock. A reliably correlated source remains bound to its source session regardless of selection changes. Reply-choice callbacks are short opaque, one-time volatile tokens bound to their authorized private chat, sender, and exact choice message. Correlated source-message mappings and pending reply choices are bounded and nonpersistent; stale/unknown naming replies and callbacks never reach Pi. A transient/uncertain panel-edit failure is not retried by sending a duplicate panel; the transport marks the panel stale and provides an explicit Refresh action while keeping operation execution separate from panel presentation. Refresh from either the panel or its notice edits only the stored panel message ID and never adopts or pins the notice. Any confirmed successful existing-panel edit clears the stale notice state. An explicit “message to edit not found” response permits creating a replacement panel. Once a replacement message is created, its ID is saved even if later keyboard publication fails; confirmation intents for a failed publication are dropped, and the next `/menu` refresh targets the known replacement. Pin failure leaves `/menu` and slash commands available and reports that the panel is unpinned.
- Completed assistant output is buffered as a whole turn. If a chat's input was accepted or has uncertain delivery for that run/turn and the chat switches away before delivery, the answer is delivered once as a `Фоновая сессия` with the session name and full ID and a one-time, revalidated `Переключиться на эту сессию` action; if the session is selected when delivery occurs, output is presented normally without a duplicate. Definite submission rejects do not attribute a run. Attribution is keyed by the actual `InputId` and observed pending/accepted/uncertain lifecycle events, not a pre-dispatch running snapshot; records are bounded, terminal completion/failure/cancellation retires an ID, and uncertain delivery is resolved at its associated run's settlement. A steered input still pending when its current run settles is detached from that run and associated with the next observed `agent_start`; if it completes or fails before that run starts, it is retired and cannot leak into a later unrelated run. A submission held behind cancellation is associated only after its pending event occurs after the abort gate. When a run has attributed submitters, only those chats receive its completed answer; when no Telegram submission is attributed, selected chats receive ordinary session output. Recipient tracking is volatile, bounded, and isolated per chat. Exact `PI_SUBAGENT_ASYNC_JSON:` envelopes are redacted from streamed assistant output and Pi `setWidget`/`setStatus`/`notify` notification text. Bounded physical-line framing recognizes the optional exact `Pi:` prefix and marker after leading whitespace without retaining an unbounded raw prefix. An eligible oversized envelope is discarded through its physical-line delimiter only after the complete prefix and marker are confirmed; a partial prefix that diverges into prose or a lookalike follows ordinary visible-output and queue-overflow/omission behavior, and subsequent lines continue to be processed. Fenced-code markers and prose/inline lookalikes are preserved. For an attributed Telegram turn, every relevant allowlisted safe role/state in a snapshot is normalized into its per-role semantic slot; approved-role tool fallback coalesces with that slot. Raw envelope, IDs, and task suffixes remain hidden, and no new message, background bubble, or un-attributed status message is created. A turn containing only widget lines sends no answer. The body is followed by a blank line and a searchable `Name · <full SessionId>` footer (or only `<full SessionId>` when unnamed); the full session ID is rendered in monospace with a Telegram code entity and no `#` tag. Restarted historical footer names are validated against generated single-line name syntax, not mutable current session metadata, while bot identity, full ID, exact code entity, and multipart structure remain required. For each Telegram-triggered turn, one reply activity bubble is edited in place with the session name when present and full `SessionId`, and shows Pi input state, meaningful bounded operation summaries/outcomes, notifications, and available model/effort/usage/context values; it is deleted only after the separately delivered final answer and session settlement. Activity rows suppress generic `subagent · workflow` and subagent management/status/list/wait/steer/resume/control calls unless a safe display label is approved, as well as duplicates, terminal-to-running regressions, heartbeat, unchanged polling, unknown ends, and raw arguments/IDs. Only meaningful ordinary tools appear. Approved safe child roles use one semantic slot per role (optionally displaying a safe label); equivalent tool rows are coalesced into that slot, and a child slot takes precedence over a duplicate tool row. Exact tool-call IDs update one row in place from running to done/failed; repeated or out-of-order terminal updates are ignored, and turn reset clears the ledger. Suppressed events do not consume row bounds, overflow counts, or update time. The combined projection is capped at six operation rows, preferring running and failed rows over older successes; omitted distinct rows are counted truthfully by state (`Ещё выполняется`, `Ещё ошибок`, `Ещё завершено`). The exact-ID ledger retains at most 256 records; further distinct calls are not tracked and an explicit untracked-operations marker is shown. The bubble ends with `Обновлено: HH:mm:ss` in host local time; it changes only when the semantic projected content changes (including thinking, meaningful operation/child state, visible notice/input/status/usage), not for duplicate events or identical polling. Queued renders preserve the latest semantic timestamp, including across a render already in flight. Existing redaction and truncation defenses apply; internal IDs and raw arguments are never shown. RPC prompt acceptance is not presented as proof that a queued input has started; run settlement is session-scoped. Routine `agent_start`, `agent_end`, and `agent_settled` lifecycle fragments are not emitted separately. Safe detailed errors, harness recovery statuses, and input-delivery notifications remain visible and session-correlated; identical errors are deduplicated until recovery. Completed assistant-turn bodies render common Markdown as safely escaped Telegram HTML: emphasis, strike-through, inline/fenced code, and HTTP(S)/mailto links. Raw HTML is escaped; unsupported schemes and malformed markup remain non-clickable and readable. This conversion applies only to final assistant output; commands, input acknowledgements/activity bubbles, statuses, and errors keep their existing presentation. The session footer ID remains monospace. Raw reasoning and stderr are never echoed. A submit diagnostic may include its exactly correlated input text in the private chat, but prompt contents are never logged or persisted. Model/workspace output is not universally redacted and may contain sensitive workspace data.
- If a whole turn exceeds Telegram's 4096-character limit, it is split into ordered parts. Each part fits within the limit, repeats the monospace session-ID footer, and includes its `i/N` marker; chunk boundaries preserve Unicode surrogate pairs and content is not resent. Overflow remains bounded and is reported explicitly; when background output is omitted, its overflow notice retains background delivery eligibility and the session-switch action.
- Runtime operation failures include an actionable safe summary plus exception type, stack, and nested causes when safe; their journal entry carries the operation kind and a short correlation reference. Pi startup/control wrappers intentionally omit raw Pi provider causes and stderr, while preserving the typed failure and harnessd stack. Telegram sends error replies as escaped HTML `<pre><code>` blocks, bounded below Telegram's 4096-character limit; exception text is treated as literal text, never markup. Known Telegram update and callback failures include a correlation reference and traceback. Diagnostics redact the configured bot token, token-shaped strings, and common credential assignments. Submitted prompt text is excluded from logs and persistent state; it may appear only in the private, exactly correlated submit-error reply. Paths may appear in diagnostics. A failure to send a diagnostic is best-effort and does not change operation semantics.
- Successful text, photo, and document submissions show the `InputId` state in the editable activity bubble and add an `👀` reaction to the originating Telegram message after Pi confirms acceptance (including queued acceptance). The reaction means accepted by Pi, not completed. If Telegram cannot set the reaction, harnessd logs a safe diagnostic; the activity bubble still provides the acknowledgment. Rejected or uncertain submissions are not reacted as accepted. Event notifications are queued per chat in session-event order and recheck at send time that the chat still selects that session. This selection filter does not suppress a run's explicitly attributed final answer: it is delivered once to its accepted/uncertain submitter, with the background-session presentation and switch action when the chat no longer selects that session. The successful submit result supplies the single `InputId` acceptance confirmation; the subsequent `accepted` event is not echoed as a duplicate. Repeated states for one input may be coalesced only at the newest event position, preserving the relative order of retained output/status/input notifications. Identical generic error events are shown once per failure episode and become visible again after `harness_recovered`.
- Each chat has a bounded queue (32,768 pending characters, bounded message/control counts) and each API send has a 5-second deadline; failed message sends produce a redacted diagnostic with a correlation reference, while the activity bubble reports non-delivery and no retry occurs. Excess output is discarded with a safe omission notice keyed to the omitted item's session and background-delivery context, never the incoming item; distinct contexts retain separate notices with their own session footer and switch action. Input-delivery control items receive reserved capacity and output is evicted first. If a chat's event send times out/fails, that chat's event queue is disabled until an explicit reset or service restart; other recipients and core event delivery continue. While disabled, new text and media submissions from that chat are blocked, but management/menu actions remain available. The disabled state is rechecked under the per-session lock immediately before dispatch, after any lock wait or media download; a reset enables only future events and takes effect at that same dispatch boundary. `/menu` offers `Включить канал для новых событий`; reset discards any queued remainder and enables only new events, never replaying old events. Direct command replies are best-effort and time-bounded too.
- Submit uncertainty is reported with the original `InputId` in the safe correlated error result and/or event notification. Presentation says Pi may have accepted the input but its acknowledgement was lost, and that no automatic resend occurred; definite rejection remains distinct. No automatic resend occurs. New operator inputs may still be submitted to Pi's native queue after an uncertain delivery; the uncertain input itself is never resent. A failed input event whose detail is `Input canceled` is presented as canceled by the user, not as a send error. While multiple inputs are outstanding, `/cancel <inputId>` is refused with an explanation because Pi RPC cannot cancel one queued item without aborting the run; no run or queued input is canceled. A new message arriving during a single-input cancellation is submitted to Pi after the abort response, preventing the run-wide abort from discarding it. If cancellation's response is uncertain, the message waits until Pi settles or exits before submission. An overflowed notification cannot cause an uncertain input to be resent.

## Polling lifecycle and failure behavior

- CLI startup initializes grammY with an abort signal before beginning long polling. A startup signal aborts initialization and runtime startup rolls back. After readiness, an unexpected fatal polling exit requests safe runtime shutdown; the CLI does not silently leave a non-polling runtime active.
- A SHA-256-derived, non-secret lock filename is created exclusively under the supervisor state directory. Its mode is `0600` and its content is only the owner PID. A second harnessd process sharing that state directory is rejected. A stale owner is removed only when the PID is demonstrably absent; ambiguous or unrecoverable lock/recovery state fails closed.
- `SIGINT`/`SIGTERM` stop the runtime. Polling stop, initialization, and notification shutdown are awaited within bounded deadlines. The lock is released only after polling termination is confirmed; incomplete cleanup retains ownership rather than allowing a second poller. Telegram API conflicts with an unrelated poller are treated as fatal; this local lock does not prevent another program from using the same bot token.
- Persisted session rows are not sufficient to prove that a Pi process is live. While the supervisor is alive, core provides bounded native-session recovery and sends the fixed status events above; Telegram only presents these events and does not own retry policy. A graceful shutdown leaves session records stopped; Telegram restores chat selections on restart, but does not launch Pi until a new input or explicit `/resume`. After an unclean supervisor exit, saved rows may remain `running`; this milestone does not reattach or restart those processes, and a failed submit is explained without resending or creating a replacement.

## Incoming files and typing

- Authorized private-chat documents and photos are acknowledged immediately with `Получаю вложение…`, then downloaded through Telegram's `getFile` path with a 60-second total deadline and the 20,000,000-byte limit; photos use the highest-resolution available `PhotoSize`. Network download occurs outside the session inbox lock. Before saving/submitting, the transport reacquires the lock and revalidates the target/selection rule, lifecycle, and inbox quota; a timeout explicitly says the file was not submitted and never retries automatically. Files are written with collision-resistant names and private permissions under `$HARNESSD_STATE_DIR/inbox/<SessionId>/`, and submitted with a local inbox path and optional caption as untrusted prompt text. Incoming bytes never enter the workspace or SQLite; if the per-session state-directory inbox destination would fall within the session's canonical workspace, the upload is rejected before creating or writing it. Photos are also passed transiently to Pi as image content. Each session inbox is limited to 10 files and 100 MiB; over-quota uploads are rejected without evicting retained files. Files expire seven days after receipt. Cleanup runs at startup and hourly, rechecks the lifecycle state under the per-session inbox lock shared with uploads/resume/submission, skips running sessions, and removes the inbox on stopped-session deletion; a stopped session's old inbox path is therefore not guaranteed to remain available beyond the TTL. Incomplete temporary files are removed; unsupported, missing-selection, oversized, quota, download, and write failures receive fixed actionable replies without submitting partial content.
- While Pi reports an agent turn active, the transport refreshes the Telegram `typing` action for authorized chats currently selecting that session. It stops for chats on deselection and on turn settlement, error, or transport shutdown. If a chat reselects a session while its turn remains active, typing resumes for that chat.

## Non-goals and related contracts

Groups/channels, persistent event history, per-user session ownership, automatic input retries, Telegram-owned watchdog policy, recovery of stale running processes after an unclean supervisor exit, sandboxing, and secret-wallet behavior are not provided by this surface. CLI environment loading and user-level service management are defined by [CLI configuration](cli-configuration.md) and [user service](user-service.md). See [core session management](core-session-management.md) and [Pi RPC harness](pi-rpc-harness.md).
