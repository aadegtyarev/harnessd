# Surface contract: Telegram transport and CLI

## Boundary, consumers, and ownership

`TelegramTransportAdapter` in `src/telegram-transport.ts` implements the generic transport port. It owns Telegram parsing, sender/chat authorization, per-private-chat session selection and persistence, safe result/event presentation, long-polling lifecycle, and a token-derived polling lock. `src/cli.ts` validates configuration and composes one adapter with `ApplicationRuntime`; core and Pi RPC do not import Telegram code. Generic request/result/event guarantees are defined by [transport adapter](transport-adapter.md).

## Configuration and authorization

- Runtime startup loads an optional `.env` from the process current working directory before validating configuration. Process-environment values take precedence, file values are parsed as Node dotenv syntax (never executed as shell), and read errors are reported without exposing contents. See [CLI configuration](cli-configuration.md).
- `HARNESSD_TELEGRAM_BOT_TOKEN` and a nonempty comma-separated `HARNESSD_TELEGRAM_ALLOWED_USER_IDS` are required. IDs must be positive safe integers. `HARNESSD_PI_EXECUTABLE` defaults to `pi`; `HARNESSD_DEFAULT_HARNESS` selects the default registered harness ID or alias (default `pi-rpc`); `HARNESSD_STATE_DIR` uses the core's standard resolution; `HARNESSD_HOME` optionally selects the initial per-chat directory and `/new` default; it defaults to `/` and is not a filesystem boundary. `harnessd --help` reports usage without requiring or loading configuration.
- `HARNESSD_EXECUTION_MODE` defaults to `direct` (trusted; `cwd` is not a sandbox). The CLI accepts only `direct` or `isolated`; because it registers no isolation provider, an isolated request fails safely before transport startup. Invalid values are rejected before configuration-driven transport construction.
- Every Telegram update, including callback queries, passes middleware before handlers: the sender must exist, have a positive safe numeric ID in the allowlist, and the chat must be `private`. Unauthorized/missing/malformed senders and groups/channels receive no reply, session data, or core dispatch.
- Allowlisted operators share access to all local sessions. The bot token is not logged or passed to Pi; child environment behavior remains the process-provider contract. Direct Pi is trusted local execution with the supervisor user's OS permissions; `cwd` is not a sandbox.

## Commands and session routing

- Supported commands: `/start`, `/help`, `/menu`, `/rename [sessionId] <name|--clear>`, `/sessions`, `/new [@harnessAlias] [cwd]`, `/ls [path]`, `/cd [path]`, `/send <path>`, `/use [sessionId]`, `/resume [sessionId]`, `/inspect [sessionId]`, `/status`, `/model [provider/modelId [effort]]`, `/effort [level]`, `/permissions [mode|default]`, `/reload`, `/stop [sessionId]`, `/delete <sessionId>`, and `/cancel [inputId]`. Bare `/cancel` invokes current-active-run cancellation for the selected session; explicit `/cancel <inputId>` requests cancellation of that exact input and retains its ambiguity protections. Authorization and selected-session routing remain unchanged. Cancellation requires the declared `harness.cancel` capability; unsupported sessions reject manual use and hide `/cancel` from per-chat help/menu. `/reload` likewise requires `harness.reload`, is hidden from selected-session help/menu when absent, and unsupported manual invocation is rejected before dispatch; Pi retains it where declared. Global menus retain native `/reload` until a session is selected. `/start` sends a Russian welcome with one-time workflow buttons bound to the authorized chat, sender, and exact welcome message; the buttons open or refresh the actual panel/session view or start the naming flow. The welcome message is never adopted, persisted, or pinned as the panel. If `/use` has no ID, it confirms the remembered selection or explains how to choose one; missing-selection replies link to `/sessions` and `/menu`. The shared visibility-tagged catalog generates CLI help and the native Telegram `/help` and menu entries; selected-session extension commands are added dynamically to Telegram `/help` and each chat's command menu. Registration is best-effort; failure emits a correlated redacted diagnostic but does not prevent polling or manual command handling. Plain text and media submit to the session selected by that private chat. A reply to a reliably correlated bot final-output or activity message routes directly to that source session even when another session is selected; it does not change selection or ask for a routing choice. After restart, a reply may route only from a message authored by this bot whose exact generated final-output footer and single SessionId code entity match a known session; named and unnamed multipart footers (including valid ` · i/N` suffixes) are recognized. User or other-bot lookalikes are unknown. An unknown reply source is never guessed: the operator must explicitly choose the current selected target or cancel. Correlation is volatile and bounded to the most recent 128 relevant bot messages per chat; it is not reply history and is lost on restart. Replies to active naming ForceReply prompts are handled as names; superseded, expired, and stale naming replies, including media and replies after restart, never submit to Pi. If a selected session is deliberately stopped, core resumes that exact saved Pi-native session before submitting only the new input once. After a graceful service restart, the transport restores each chat's saved selection without starting Pi at transport startup; the first new input triggers core's normal resume path. If Pi is already working, the Pi RPC harness submits the new input to Pi's native steering queue rather than rejecting it or holding a second harnessd queue. `/resume` does not change selection and never falls back to a new session; its success reply explicitly says selection is unchanged and states the ordinary-message target. It offers a Select callback only when the resumed session is not already selected. Lifecycle replies identify the operation outcome, selection effects, and next message target/action. `/model` and `/effort` list available/current controls for the selected live session; on a stopped session they explain that a running Pi is required and direct the operator to resume, then select as needed. Model IDs are selected by stable `provider/modelId`, never by display name. Generic descriptor-driven adapter options are inspectable and mutable through available controls; changes restart and resume the same idle session with its exact saved native ID, never replay input, and dangerous values require explicit confirmation. Claude's `/permissions` lists native permission modes, `manual` selects native `default` (which enables one-shot manual prompts), and `/permissions default` resets the explicit override. A Claude tool permission request is correlated to the active native session, turn and request, expires, and is answered once; allow preserves the exact original tool input, deny does not automatically interrupt the run, and timeout/cancel/stale requests fail closed. Confirmed `bypassPermissions` requires explicit operator confirmation.
- Pi extension commands are discovered from the selected live session only, freshly for `/help` and again before dispatch; dispatch discovery and availability validation finish before the prompt is enqueued. Only Pi entries marked `source: extension` are eligible. Prompt templates and skills are excluded, native harnessd names win collisions (including `/reload`), and `/cost` appears only when supplied by an extension. Help rechecks selection and inventory currency before presenting dynamic entries; absent selection or discovery failure yields native-only help with safe guidance. Dispatch uses only the chat's currently selected session and never resumes or creates one. It sends Pi `prompt` as `/{name}` plus the exact original raw remainder after the command token, preserving spacing without tokenization. Immediately before writing, the adapter synchronously checks selected-session currency and lifecycle, process, reload, abort, and cancellation state; it does not rediscover or revalidate command inventory there. A command queued behind cancellation waits for the abort gate. Ordinary Pi busy state is allowed. A pre-write rejection is definite; after write, timeout/unknown disposition is uncertain. Acknowledgements say only that Pi accepted or handled the command, not that work completed; errors are bounded and safe, and no command is retried. `sourceInfo` and filesystem paths are never exposed.
- Each chat's Telegram command menu starts with native entries and appends sorted, sanitized selected-session extension entries, capped deterministically at 100 total. A selected session's declared capabilities determine visibility of `/cancel` and `/reload`; capability lookup failure hides both. No selection or extension-discovery failure publishes native entries only. Menus refresh on selection changes and session create, resume (including implicit resume preceding submit), reload, recovery, stop, and delete transitions, for chats selecting the affected session. Publication is coalesced per chat and superseded requests are discarded. A publication that times out is quarantined until its underlying API call settles; after either settlement outcome, the newest menu intent is published unless shutdown has begun. While unresolved, that chat's menu may remain stale; polling and manual command handling remain available. Shutdown suppresses replay.
- `/new` accepts an optional leading `@alias` token followed by an optional `cwd`; the known harness alias is resolved separately and create receives its canonical harness ID, while omission leaves configured-default resolution to core. An unknown alias fails explicitly without falling back to the default. The remaining path text is preserved as one `cwd` path, including spaces; one matching pair of outer single or double quotes is stripped. Unmatched leading quotes receive a safe syntax hint. It performs no shell execution or expansion other than `~` and `~/...` to the operating-system user's home. Without a path, `/new` uses that chat's current directory, initially `HARNESSD_HOME` or `/`; the generic runtime default harness is used for new sessions. Explicit relative paths resolve from the same chat directory, and absolute paths are accepted. `~` expansion is independent of `HARNESSD_HOME`. Core canonicalizes and validates either path. `/use` inspects before selection, and a failed lookup leaves the existing selection unchanged. Selection changes from `/use`, `/new`, and `/menu` are persisted per authorized private chat; bare `/use` inspects and confirms that saved selection. Explicit stop clears the selected chat's saved choice, and successful deletion clears every chat selecting the deleted session. Missing-session and persistence failures are reported with actionable guidance. Inspect/stop default to the selected session; cancel requires a selected session and exact `InputId`. Successful `/stop` clears that chat's selection when it stopped the currently selected session. Slash and confirmed panel Stop replies provide a one-time Resume-and-select callback bound to the authorized chat, sender, message, and session; it rechecks that the session remains stopped before resuming, and selection persistence failures are reported as partial success.
- `/reload` takes no arguments and targets only the selected session for that private chat. It reloads Pi resources without changing selection or restarting a process, and reports the session name/full ID plus the actual current ordinary-message destination. Selection is revalidated at the dispatch boundary; a change before dispatch aborts safely, while completion remains bound to the original session. Busy, unsupported, unavailable, and unconfirmed outcomes use fixed safe guidance; no reload is automatically retried.
- `/ls [path]` lists immediate files and folders in the supplied or current chat directory, hides dotfiles by default, bounds output to 100 entries, and never reads file contents. `/cd [path]` changes only the current chat's volatile navigation directory; `/cd` without a path goes to the OS user's home. Relative paths use the chat directory and absolute paths, `..`, and symlinks can reach any directory accessible to the service OS user. `HARNESSD_HOME` only selects the initial directory; it is not a sandbox. `/cd` does not change the cwd of running sessions. `/send <path>` uploads a regular file from the selected session's canonical cwd to that authorized private chat only; relative paths resolve against the session cwd, paths outside it are rejected, and files over 20 MiB or non-regular files fail safely. The Pi and Claude `send_file` tools explicitly send a regular workspace file (optionally with a caption) to authorized private chats currently selecting that session; both use the same session-scoped `AgentFileSendHandler`, canonical-workspace, symlink, regular-file, and 20 MiB checks. Claude receives only the tool when this handler is available; its MCP bridge forwards once and reports partial or uncertain delivery without retry. Telegram identities and credentials are not exposed to the harness. Outer matching quotes may surround a path containing spaces.
- Session names are optional, shared metadata in the harnessd SQLite record, independent of Pi-native data and `cwd`. They are trimmed, single-line, nonempty when set, and limited to 64 Unicode code points; duplicates are allowed. `/rename [sessionId] <name>` targets the explicit ID or selected session, and `--clear` removes the name. `/sessions` shows a selected marker, name plus short ID (or short ID), lifecycle status, and compact cwd; `/inspect` retains `Name · #<full SessionId>` (or `#<full SessionId>`) and cwd while escaping HTML and abbreviating displayed cwd paths after 600 Unicode code points. `/delete` requires one explicit ID and removes only a stopped harnessd metadata row; it neither stops a live session nor deletes Pi-native files or its `cwd`. Its confirmation states that the harnessd record and received inbox attachments are deleted while workspace and Pi-native files remain. A non-stopped record returns guidance to `/stop` it first. Successful deletion clears volatile selections for that ID and removes its inbox; if filesystem cleanup fails, deletion remains successful and the transport reports cleanup as pending for a later sweep. `/status` reports the name when present, full `SessionId`, saved cwd/lifecycle, and live model, effort, aggregate usage, and estimated USD cost; missing live data is marked unavailable, cost is not provider billing, and optional plugin-only per-model/subagent details are excluded. A partially successful model change is reported without claiming rollback.

## Session panel, event presentation, and backpressure

- A persistent reply keyboard (`is_persistent`) under the input field offers `📊 Ход`, `📋 Панель`, `✋ Прервать`, `🗂 Сессии`; it is sent before the `/start` welcome and with the first `📋` press in a process. Pressing a button is handled as a command (never submitted to Pi, including when Telegram sends the tap as a reply) and the button message is deleted best effort: `📊` shows `/status`, `🗂` shows `/sessions`, `✋` asks for an inline confirmation bound to the chat, sender, message, and selected session that expires after 2 minutes (a stale tap reports that nothing was cancelled) before running `/cancel`, and `📋` publishes the panel at the bottom of the chat (see `/menu` below). Overflow notices of silent deliveries are silent too. Mid-run assistant messages are delivered without notification sound; the answer delivered at run settlement keeps it.
- `/menu`, `📋`, and the `/start` welcome panel action publish one inline panel per authorized private chat as a fresh message at the bottom of the chat; the `/menu` command message is deleted best effort. Only after the new panel is confirmed is the previous panel retired and deleted; if Telegram refuses the delete (for example, a message older than 48 hours), the old message is edited to «Панель перенесена ниже ↓» without buttons, and if that also fails its taps report an outdated panel and refresh the current one. If the new panel is not confirmed, the previous panel stays the panel and no duplicate remains. Overlapping bottom publishes in one chat leave exactly one current panel; a superseded publish never restores or edits the previous panel. Automatic refreshes, in-panel navigation, the stale-notice refresh, and restart restore edit the current panel in place. Panels are not pinned (a pinned legacy panel being replaced is unpinned). It explicitly distinguishes the selected session (plain-message destination), preview session, and exact new-session creation directory. Previous/next change preview only; **Выбрать** alone commits preview as the selected session. Preview controls for model, effort, stop, delete, and resume address that preview session, independent of selection. Session-list failure is reported and preserves current and persisted selection; only a successful list that authoritatively omits the selected ID may clear it. Session panels distinguish record existence, per-chat message selection, and persisted Pi lifecycle status (running, stopped, starting/recovering, or failed/stale); a running record may be stale after an unclean supervisor exit and is not proof that Pi is live. Running-status sessions offer Stop and live controls; stopped sessions offer Resume, combined Resume and select, and Delete; non-stopped sessions do not offer Delete. Model/effort panels require a running Pi. Failed/stale sessions offer only core-supported stop/inspection recovery, never reattachment or replacement. The panel shows live parent-session usage when available (`↑` input, `↓` output, `R` cache reads, `CH` cache-hit rate, estimated cost, and actual context occupancy from Pi RPC `contextUsage`). Missing or null values display as unavailable, never as zero; subagent metrics are not available through supported harness interfaces. Preview and folder navigation are volatile. The bot-token-scoped private state file stores panel message IDs and per-chat selected session IDs (never prompt bodies); version-1 panel files remain readable and are upgraded on the next write. Panel layout: `✉️ Сообщения → <name · #8-char id>` (or `никуда (сессия не выбрана)`), a `━━━━━━━━━━━━` separator, `👁 Просмотр:` (`та же сессия` when it equals the selection), the preview folder, one combined Russian `Статус:` line, live usage/model/effort when available (a failed live query adds one line), another separator, then `Новые сессии создаются в: <folder>`. Full session IDs stay in session details and answer footers; preview action buttons are labelled `Модель`, `Усилие`, `Переименовать`, `Остановить`, `Возобновить и выбрать`, `Удалить…`. Whenever the panel shows a preview session it offers `Переименовать` for that session (in the `Модель`/`Усилие` row for running or stopped sessions, otherwise in its own row; absent when no session is shown); it is bound to the session shown at render time and starts exactly the session-card rename flow (same prompt, reply handling, cancel, `--clear`, and not-found handling), after which the panel reflects the new name.
- Panel live status is scoped to each chat's preview, independently of its selected ordinary-message destination; preview navigation and live-status refresh never change selection, while **Выбрать** explicitly commits the preview as the ordinary-message destination. It queries that preview for current lifecycle/live metrics and derives busy/idle from agent events, with reload/recovery activity shown while owned. On startup, a persisted running record is stale until queried; absent metrics or query failure are unavailable, and offline is shown only when a successful session listing confirms there are no sessions. Starting, recovering, stopped, failed/stale, live-unavailable, offline, idle, and busy remain distinct; records alone never prove Pi liveness. Agent start/settled and recovery/fatal events, plus relevant create/resume/stop/delete/reload/preview/menu actions, refresh only chats previewing the affected session; stale generations and preview changes prevent late queries from overwriting newer intent. Per-chat renders coalesce newest-wins and deduplicate identical text plus keyboard. Telegram edits are serialized, spaced by at least 500 ms, and a waiting render becomes dispatch-ready within 2 seconds; that bound excludes a strict single-flight call already in flight, which is not canceled or overlapped and retains its existing 5-second API deadline, together with that call's transient-failure retry backoff. Once it completes, the newest queued render follows subject to spacing. Terminal lifecycle and explicit user actions flush. The displayed local `Обновлено: HH:mm:ss` changes only when projected visible lifecycle/activity/live semantics change, not on duplicate events or identical polls. Shutdown invalidates pending work and awaits bounded in-flight refreshes. A transient panel edit failure (deadline, network, 5xx, or HTTP 429 whose `retry_after` is at most 10 s) is retried up to twice (500 ms × attempt or `retry_after`), because re-editing is idempotent; the panel is marked for repair from the first failure so a later identical render is never deduplicated against an edit that may have landed; if retries are exhausted or superseded, no notice or duplicate panel is posted and the next refresh repairs it. Repair is invisible: the in-panel stale line and its refresh button appear only for operator-visible staleness (a posted notice after a definite rejection, or a panel restored after restart). Only a rejection meaning the old message is gone or frozen (message to edit not found, message can't be edited, MESSAGE_ID_INVALID) publishes a fresh panel and best-effort unpins the frozen predecessor; any other definite edit rejection keeps the stored panel, marks it stale, and posts the notice with an explicit refresh button. A panel send is not retried within the same render; an uncertain send failure is silent, while a definite send rejection posts the notice. A created replacement ID is saved even if keyboard publication fails, and failed publication intents are dropped; later refreshes edit that replacement and a later `/menu` replaces it with a fresh bottom panel.
- Inline panel routes include session list/details, folder navigation, new-session creation with a transport-neutral harness choice and optional name, model/effort selection, and stop/delete actions with button-level confirmation. The panel choice passes the canonical harness ID through its name flow; its one-time callbacks are bound to the authorized chat, sender, and exact choice message. Folder navigation lists directories independently from `/ls`, shows at most 100 directories, reports that limit, and guides access to further paths with `/cd <путь>`; `/ls` retains its mixed file-and-directory listing bounded to 100 entries. The session list marks the selection and shows name or short ID, lifecycle, and compact cwd; details retain the full ID. The new-session panel shows the creation directory in a bounded display (an ellipsis marks truncation). Creation prompts preserve repeated whitespace and visibly escape control characters; if the exact path cannot fit in one Telegram message, it is sent in bounded consecutive path messages before a short ForceReply prompt. The cwd dispatched for creation remains the exact original path. Initial and reissued create/rename name prompts display the complete escaped cwd; when it cannot fit alongside prompt instructions in one Telegram message, the exact path is sent in bounded consecutive path messages before a short ForceReply prompt, without changing the dispatched cwd. Folder buttons carry short opaque, volatile tokens bound to the authorized chat, panel message/generation, parent directory, and exact displayed target path; they never resolve a fresh-list index. Rerendering or replacing panel context invalidates them, and stale taps do not navigate and offer panel refresh. Stop/delete confirmation tokens are one-time and volatile, bound to chat, panel message/generation, session, action, and expected lifecycle; cancel, panel rerender, use, success, and observed lifecycle changes invalidate them. Post-stop Resume-and-select callbacks are also one-time, volatile, and bound to chat, sender, the exact action message, session, and lifecycle epoch; stale, replayed, and cross-chat callbacks do not act. Resume-and-select retains its epoch reference through inspect, resume, and selection, rechecking invalidation before each consequential step; failure leaves selection unchanged and is not reported as success. Direct-message Resume-and-select and Resume Select callbacks do not replace or pin the direct action message as the panel; they refresh the chat's existing panel when one is stored. Direct Select callbacks are one-time and bound to the authorized chat, sender, session, and exact action message. Panel Resume feedback distinguishes when the resumed session is already the ordinary-message target from when it is not. Epoch state is retired when no pending confirmation or in-flight confirmation operation references the session; in-flight operations retain their invalidation epoch until completion. Before acting, confirmation rechecks the session lifecycle. Stale, replayed, canceled, or state-mismatched confirmations have no side effect and require fresh intent. Tokens are not persisted, so restart invalidates them. The same core operations and safety checks as slash commands apply. Unauthorized and non-private callbacks are rejected before core dispatch. Malformed session IDs and callbacks targeting a session absent from the transport's current in-memory session set are also rejected before dispatch; stale session buttons offer a `/menu` refresh. Name prompts use ForceReply and identify the exact session target and cwd. Each private chat has one active naming flow; a new flow explicitly supersedes the prior one. Invalid input or operation failure reissues the flow against the same target. Create prompts offer Create unnamed and Cancel inline buttons; rename prompts offer Cancel, while clearing a name remains a separate action. Prompt identity uses the complete, anchored generated ForceReply envelope, including its complete instructions and exact named or unnamed target identity, not a marker or short prefix; cwd presentation characters including Unicode line and paragraph separators remain matchable. Known correlated activity/final-output reply routes take precedence over prompt-envelope detection. Stale text/media replies matching current Russian envelopes or complete historical English envelopes remain recognizable and are rejected after restart without persisted prompt state. After an explicit one-time cross-session reply-choice callback, the retained incoming media is dispatched to the confirmed source/selected destination without reclassifying its original reply; download begins only after confirmation. If the source already equals the selected session, only the selected-destination choice is shown. A confirmed-current route snapshots that selection and revalidates it under the inbox lock after inspection immediately before saving and again immediately before dispatch; if selection changes before saving, nothing is written or submitted, and if it changes after saving the newly saved file is safely removed under the lock. A reliably correlated source remains bound to its source session regardless of selection changes. Reply-choice callbacks are short opaque, one-time volatile tokens bound to their authorized private chat, sender, and exact choice message. Correlated source-message mappings and pending reply choices are bounded and nonpersistent; stale/unknown naming replies and callbacks never reach Pi. A transient/uncertain panel-edit failure is never repaired by sending a duplicate panel; it is retried and then repaired invisibly by the next refresh, while a definite rejection marks the panel stale and provides an explicit Refresh action, keeping operation execution separate from panel presentation. Refresh from either the panel or its notice edits only the stored panel message ID and never adopts or pins the notice. Any confirmed successful existing-panel edit clears the stale notice state. Only a rejection meaning the old message is gone or frozen (message to edit not found, message can't be edited, MESSAGE_ID_INVALID) permits creating a replacement panel. Buttons of a panel replaced in the current process never re-adopt it as the panel: the tap is answered with a short "panel is outdated, press 📋" notice and the current panel is refreshed. Once a replacement message is created, its ID is saved even if later keyboard publication fails; confirmation intents for a failed publication are dropped, and the next refresh edits the known replacement (a later `/menu` publishes a fresh bottom panel and retires it). A panel message whose send lands after another panel became the chat's panel (for example, the operator tapped the old panel meanwhile) is retired and deleted, or stripped of its buttons if the delete fails, so only one live panel remains.
- Assistant output is buffered per assistant message: each `message_end` status delivers the text buffered since the previous boundary while the run continues (Pi task continuations can keep one run open for hours), and settlement delivers only the remainder, without duplicates or a separate lifecycle message. A mid-run message goes to the chats whose inputs are attributed to the run (accepted/uncertain or already completed), otherwise to the selected chats; canceled-run suppression applies only to text not yet delivered. A successful stop (command or panel) first delivers remaining buffered text with the interrupted marker, waits for that chat queue, then clears the selection. The overflow bound applies per delivered message, not per run. If a chat's input was accepted or has uncertain delivery for that run/turn and the chat switches away before delivery, the answer is delivered once as a `Фоновая сессия` with the session name and full ID and a one-time, revalidated `Переключиться на эту сессию` action; if the session is selected when delivery occurs, output is presented normally without a duplicate. Definite submission rejects do not attribute a run. Attribution is keyed by the actual `InputId` and observed pending/accepted/uncertain lifecycle events, not a pre-dispatch running snapshot; records are bounded, terminal completion/failure/cancellation retires an ID, and uncertain delivery is resolved at its associated run's settlement. At settlement of a bare current-run cancellation, preserved pending or accepted steered inputs are detached from the canceled turn and associated with the next observed `agent_start`; they remain attributed to their original submitting chats even if those chats switch sessions. Truly completed or canceled inputs are not moved. Confirmed canceled-run output is suppressed rather than reassigned to the next turn. If a detached input completes or fails before that run starts, it is retired and cannot leak into a later unrelated run. A submission held behind cancellation is associated only after its pending event occurs after the abort gate. When a run has attributed submitters, only those chats receive its completed answer; when no Telegram submission is attributed, selected chats receive ordinary session output. Recipient tracking is volatile, bounded, and isolated per chat. Exact `PI_SUBAGENT_ASYNC_JSON:` envelopes are redacted from streamed assistant output and Pi `setWidget`/`setStatus`/`notify` notification text. Bounded physical-line framing recognizes the optional exact `Pi:` prefix and marker after leading whitespace without retaining an unbounded raw prefix. An eligible oversized envelope is discarded through its physical-line delimiter only after the complete prefix and marker are confirmed; a partial prefix that diverges into prose or a lookalike follows ordinary visible-output and queue-overflow/omission behavior, and subsequent lines continue to be processed. Fenced-code markers and prose/inline lookalikes are preserved. For an attributed Telegram turn, every relevant allowlisted safe role/state in a snapshot is normalized into its per-role semantic slot; approved-role tool fallback coalesces with that slot. Raw envelope, IDs, and task suffixes remain hidden, and no new message, background bubble, or un-attributed status message is created. A turn containing only widget lines sends no answer. The body is followed by a blank line and a searchable `Name · <full SessionId>` footer (or only `<full SessionId>` when unnamed); the full session ID is rendered in monospace with a Telegram code entity and no `#` tag. Restarted historical footer names are validated against generated single-line name syntax, not mutable current session metadata, while bot identity, full ID, exact code entity, and multipart structure remain required. For each Telegram-triggered turn, one live run card (reply to the triggering message, sent silently) is edited in place. Header: state icon (⏳ working, ⏸ waiting for agents while a coordination wait runs, ❓ the /task is blocked and needs the operator), `Ход`, the input/run status, the session name and 8-character ID, and elapsed time at minute resolution. It then shows the /task goal with step/limit and the latest progress note when the harness publishes task state, the latest one-line thought (a reasoning-summary title or first sentence, ≤160 characters, never full reasoning), an agents section built from the latest pi-subagents snapshot of the session (one row per run, so parallel runs are separate rows; state icon ⏳ queued / 🟢 running / ❓ an active run that needs attention (asks the parent) / ⏸ paused / ✅ complete / ⚠️ partial / ❌ failed / ⏹ stopped / 🚫 rejected; label, 8-character ID only for generated hex/UUID run IDs, elapsed minutes, current tool and tool count for active runs; completion notices (single, detached, and grouped `Background tasks completed (N)`) yield per-agent verdicts — APPROVE/REQUEST_CHANGES from whole-word tokens near a review/verdict heading with the first P-finding, or the failed/paused/stopped state — paired with the finished run whose ID the notice carries (the async directory name or `Workflow run:`; grouped notices are split only at the `N. name` block headers the header names, so numbered lists inside a preview stay in their block, and a long notice keeps its run-ID lines when its preview is clipped); a notice without an ID is shown only when it and one unpaired finished run of that agent are both unique, otherwise no verdict is shown; a run whose step asks the parent shows ❓ and `<step> спрашивает родителя` even when the step row is cut; every top-level run gets a row before any step, steps (`↳`, ranked by their own subtree so an asking step is never cut) fill the remaining rows of at most six, and `… ещё N` counts cut rows, deeper levels and producer-side omissions; finished runs that ended before the card's turn are left out; `⏸ родитель ждёт: …` names up to three runs from running coordination waits (or all active runs for a wait without IDs) and only while the run is live; the board and verdicts are cleared when the keyed widget that carried the snapshot is cleared, when Pi restarts or recovers, and when the session is stopped or deleted), unresolved input states, notifications and child-role statuses (only when no snapshot is known), the last five of up to 40 events (thoughts; tool calls with ✓/❌/…, bash shown as `$ command → exit code · duration`; consecutive read/grep/find/ls/edit/write calls collapse into `N× … last target`; plain-language coordination rows such as `⏸ ждёт агентов #id (до N мин)`), and the usage/model/effort line followed by `Обновлено: HH:mm:ss`. Generic `subagent · workflow` and subagent management calls (`subagent_*`, `agent_list|wait|steer|resume|status|control`) never appear on the card, and an approved-role launch shows only `🚀 запустил <Role>` (no task text). Inline buttons `📋 Отчёт` (submits a short status-report request through the normal attributed chat submission, at most once per 60 s per card) and `⛔ Прервать` (cancels the current run when the session declares `harness.cancel`, otherwise reports that it is unsupported) are shown and act only while the card's run is live in its chat (between run start and settlement); otherwise the buttons are removed and taps are ignored. When a mid-run assistant message is delivered to a chat, that chat's live card is frozen in place without buttons once the chat queue drains successfully and a new card opens below the answer; if the freeze edit fails (other than message-not-found) the card stays as the live card. After the final answer and settlement the frozen pieces are deleted and the live card collapses to one line `✅ Ход завершён за … · N действий · ~$cost` (N counts every tool call of the run, with Russian plural forms). A new user input invalidates pending completion-collapse intent from an earlier turn; an older in-flight collapse cannot retire or overwrite the newer turn's card. Rate-limit and server errors on a card edit defer it instead of disabling the card. For HTTP 429 with `parameters.retry_after`, every edit of that card (including freeze and completion-collapse edits) honors the full supplied interval (including intervals over 10 seconds), suppresses API edits until eligible, and preserves the newest lifecycle intent for one single-flight edit afterward. Answer delivery itself is not delayed by card backoff. This card-local backoff does not disable or alter the chat's independent event-delivery queue. Existing redaction and truncation defenses apply; internal IDs and raw arguments are never shown. RPC prompt acceptance is not presented as proof that a queued input has started; run settlement is session-scoped. Routine `agent_start`, `agent_end`, and `agent_settled` lifecycle fragments are not emitted separately. Safe detailed errors, harness recovery statuses, and input-delivery notifications remain visible and session-correlated; identical errors are deduplicated until recovery. Completed assistant-turn bodies render common Markdown as safely escaped Telegram HTML: emphasis, strike-through, inline/fenced code, and HTTP(S)/mailto links. Outside code, block Markdown is made readable on a phone: `#`–`######` headings (marker plus whitespace; `#hashtag` stays text) become a bold line; a pipe table (header, `|---|` separator with the same column count, rows; outer pipes optional, alignment colons allowed) becomes one `• <b>first cell</b> — second cell` line per row, or `— Header: value; …` for three or more columns, with empty cells skipped, inline Markdown kept in cells, bold flattened inside the first cell, and malformed tables left as text; `-`/`*`/`+` bullets become `•` with indentation kept as nesting; a quote that starts with `> ` followed by text other than a digit or `=` (so `> 5 items` and `>= 3` stay prose) and continues over consecutive `>` lines becomes one `<blockquote>`, and a fence opened inside it is rendered as code within that quote; `---`/`***`/`___` rules are dropped. CRLF line endings are normalized first. Fenced/inline code and numbered lists are unchanged; an unclosed fence at line start (an interrupted reply) is code through the end of the message. Multipart splitting closes and reopens open `<b>`, `<i>`, `<s>`, `<a>`, `<code>`, `<pre>`, and `<blockquote>` tags so every chunk is balanced HTML. If Telegram still rejects a chunk with a 400 `can't parse entities` error, that chunk is logged and resent once as plain text (tags stripped, entities decoded, the session ID kept as a code entity); other rejections are not retried and keep the existing queue-failure behavior. Raw HTML is escaped; unsupported schemes and malformed markup remain non-clickable and readable. This conversion applies only to final assistant output; commands, input acknowledgements/activity bubbles, statuses, and errors keep their existing presentation. The session footer ID remains monospace. Full reasoning and stderr are never echoed; only one-line thought summaries are shown. A submit diagnostic may include its exactly correlated input text in the private chat, but prompt contents are never logged or persisted. Model/workspace output is not universally redacted and may contain sensitive workspace data.
- If a whole turn exceeds Telegram's 4096-character limit, it is split into ordered parts. Each part fits within the limit, repeats the monospace session-ID footer, and includes its `i/N` marker; chunk boundaries preserve Unicode surrogate pairs and content is not resent. Overflow remains bounded and is reported explicitly; when background output is omitted, its overflow notice retains background delivery eligibility and the session-switch action.
- Runtime operation failures include an actionable safe summary plus exception type, stack, and nested causes when safe; their journal entry carries the operation kind and a short correlation reference. Pi startup/control wrappers intentionally omit raw Pi provider causes and stderr, while preserving the typed failure and harnessd stack. Telegram sends error replies as escaped HTML `<pre><code>` blocks, bounded below Telegram's 4096-character limit; exception text is treated as literal text, never markup. Known Telegram update and callback failures include a correlation reference and traceback. Diagnostics redact the configured bot token, token-shaped strings, and common credential assignments. Submitted prompt text is excluded from logs and persistent state; it may appear only in the private, exactly correlated submit-error reply. Paths may appear in diagnostics. A failure to send a diagnostic is best-effort and does not change operation semantics.
- While Pi compacts its context (`compaction_start` until `compaction_end`), the live activity bubbles of a running session show the status `сжимаю контекст…`, then the status it replaced; no separate chat message is sent.
- Successful text, photo, and document submissions show the `InputId` state in the editable activity bubble and add an `👀` reaction to the originating Telegram message after Pi confirms acceptance (including queued acceptance). The reaction means accepted by Pi, not completed. If Telegram cannot set the reaction, harnessd logs a safe diagnostic; the activity bubble still provides the acknowledgment. Rejected or uncertain submissions are not reacted as accepted. Event notifications are queued per chat in session-event order and recheck at send time that the chat still selects that session. This selection filter does not suppress a run's explicitly attributed final answer: it is delivered once to its accepted/uncertain submitter, with the background-session presentation and switch action when the chat no longer selects that session. The successful submit result supplies the single `InputId` acceptance confirmation; the subsequent `accepted` event is not echoed as a duplicate. Telegram distinguishes acceptance by Pi from a prompt queued behind busy Pi work and from model consumption: queued work is labeled queued, never claimed as consumed, including during Pi background-wait (`bg_wait`-like) activity. Bare `/cancel` aborts the selected Pi session's current active run to release it; Pi-native queued inputs remain queued and are neither cleared nor resubmitted by harnessd. A queued Telegram message is not treated as model-consumed, and cancellation does not hiddenly replay/rerun that message or a background task. Repeated states for one input may be coalesced only at the newest event position, preserving the relative order of retained output/status/input notifications. Identical generic error events are shown once per failure episode and become visible again after `harness_recovered`.
- Each chat has a bounded queue (32,768 pending characters, bounded message/control counts). Ordinary message/control API calls retain a 5-second deadline; outgoing documents, from `/send` or the agent, have a separate 120-second per-recipient deadline and are aborted during stop. A slow `/send` upload holds Telegram update handling (including `/stop` and buttons) until it finishes or hits that deadline; agent-initiated sends do not. A document deadline is an unconfirmed result, not permission to retry; late settlement cannot turn that result into confirmed delivery. Failed message sends produce a redacted diagnostic with a correlation reference, while the activity bubble reports non-delivery and no retry occurs. Excess output is discarded with a safe omission notice keyed to the omitted item's session and background-delivery context, never the incoming item; distinct contexts retain separate notices with their own session footer and switch action. Input-delivery control items receive reserved capacity and output is evicted first. If a chat's event send times out/fails, that chat's event queue is disabled until an explicit reset or service restart; other recipients and core event delivery continue. While disabled, new text and media submissions from that chat are blocked, but management/menu actions remain available. The disabled state is rechecked under the per-session lock immediately before dispatch, after any lock wait or media download; a reset enables only future events and takes effect at that same dispatch boundary. `/menu` offers `Включить канал для новых событий`; reset discards any queued remainder and enables only new events, never replaying old events. Direct command replies are best-effort and time-bounded too.
- Chats hear about harness anomalies only when something went wrong; healthy tolerance stays in the journal. An oversized record handled by its type, a prompt held during compaction, and a record cut while harnessd itself stops the instance (operator `/stop`, delete, option relaunch, service shutdown) produce no chat message. A skipped record, a failed command, or a harnessd handling error (worded as a harnessd error; Pi's stream is fine) produces a plain-Russian notice to the chats currently selecting the session, through the ordered event queue with the session footer: what happened (kind, record type and size when known), what harnessd did, whether Pi keeps running, and `Журнал: harnessd, ref <ref>` matching the journal line. The journal-only head is never shown. Notices are coalesced per session and anomaly kind: the first is sent at once, repeats within the following minute produce at most one later notice with `Повторилось ещё N раз за минуту.`; pending repeats are dropped when the session is deleted or the transport stops. No icon is used because no action is required. Failures that already have a chat message are not duplicated: a rejected prompt, a hold timeout, or a held prompt Pi outlived is shown once, as the input line `Ввод <id>: не принят — Pi отклонил сообщение: <причина>` or `Ввод <id>: не отправлен — <причина>`, and the submit reply for `INPUT_NOT_DELIVERED` is suppressed for a chat that selects that session (a chat that submitted through a reply route to another session gets that one line directly). The Russian wording is picked by the harness's fixed reason code (`prompt_rejected`, `hold_timeout`, `held_and_stopped`, `canceled`), never by matching its English detail, which is shown only as a fallback for a failure without a code. The live run card shows the same line and a status matching the reason: `Pi не принял сообщение`/`вложение` for a rejection, `Отменено пользователем` for a cancel, `Не отправлено: Pi долго сжимал контекст` for a hold timeout, `Не отправлено: Pi остановился` for a held input Pi outlived, and `Сообщение не доставлено`/`Вложение не доставлено` when no code is known. A corrupted stream or a record cut by the process stopping is folded into the single stop message, which is harness-neutral Russian for every fatal session error (`Сессия остановлена: процесс завершился (<код/сигнал или «неизвестно»>).`, the cut record's type and size or that more than 20 consecutive RPC records were invalid, and the journal ref), worded by the harness's stop reason code and falling back to its English detail when no code is given; it never names Pi for a non-Pi session. The live run card shows the not-delivered input line once whichever of the input event and the submit result arrives first; other card notices are shown again when repeated. A tool whose outcome the harness could not read is shown as finished without ✓ or ❌.
- Submit uncertainty is reported with the original `InputId` in the safe correlated error result and/or event notification. Presentation says Pi may have accepted the input but its acknowledgement was lost, and that no automatic resend occurred; definite rejection remains distinct. No automatic resend occurs. New operator inputs may still be submitted to Pi's native queue after an uncertain delivery; the uncertain input itself is never resent. A failed input event whose reason code is `canceled` is presented as canceled by the user, not as a send error. While multiple inputs are outstanding, `/cancel <inputId>` is refused with an explanation because Pi RPC cannot cancel one queued item without aborting the run; no run or queued input is canceled. A new message arriving during a single-input cancellation is submitted to Pi after the abort response, preventing the run-wide abort from discarding it. If cancellation's response is uncertain, the message waits until Pi settles or exits before submission. An overflowed notification cannot cause an uncertain input to be resent.

Dynamic Pi `/cost` returns the actual bounded result to Telegram rather than only dispatch acknowledgement. The Pi adapter correlates the exact `pi-ad-session-usage:report` custom message to its single outstanding `/cost`, requires `handled` disposition, and enforces a bounded result deadline; missing/malformed/late results produce a fixed safe error and no retry. After uncertainty, the instance is quarantined from further `/cost` requests so late output cannot satisfy a later request. Raw RPC protocol/internal details are never presented.

## Polling lifecycle and failure behavior

- CLI startup initializes grammY with an abort signal before beginning long polling. A startup signal aborts initialization and runtime startup rolls back. After readiness, an unexpected fatal polling exit requests safe runtime shutdown; the CLI does not silently leave a non-polling runtime active.
- A SHA-256-derived, non-secret lock filename is created exclusively under the supervisor state directory. Its mode is `0600` and its content is only the owner PID. A second harnessd process sharing that state directory is rejected. A stale owner is removed only when the PID is demonstrably absent; ambiguous or unrecoverable lock/recovery state fails closed.
- `SIGINT`/`SIGTERM` stop the runtime. Polling stop, initialization, and notification shutdown are awaited within bounded deadlines. The lock is released only after polling termination is confirmed; incomplete cleanup retains ownership rather than allowing a second poller. Telegram API conflicts with an unrelated poller are treated as fatal; this local lock does not prevent another program from using the same bot token.
- On core's `harness_recovery_failed`, Telegram sends one failure notice to every authorized private chat (a private chat's ID is the authorized user's ID), whether or not the session is selected there; it replaces the selected-session recovery-failure status line, so one failure yields at most one notice per chat. The notice goes through the chat's ordered event queue after any flushed output, carries the session footer, and states the stored failure reason in plain, harness-neutral Russian with its fixed code (or that no cause was stored); it never contains stderr or exception text. Notices are not subject to the event-queue failure rules: each waits behind output already queued for that chat, is sent even when the chat's event channel is disabled, and a failed send (for example a 403 from a user who never opened the bot) never disables the channel; each failed delivery writes a redacted, correlated journal diagnostic. A later `harness_restarting`, `harness_recovered`, or successful restore re-arms it, so a later failure notifies again. The notice and a `failed` session card offer **Восстановить**: a volatile, bounded, one-time token bound to the authorized chat, sender, and session, reused by every notice and card render for that chat, sender, and session until it is used (not persisted; restart invalidates it). For `resume_unavailable` neither offers it; both say the session cannot be restored and suggest `/new` in that folder. Restore runs under the session request lock: it inspects the session, calls core stop unless it is already stopped (a stop error is ignored when the record is now `stopped`), then core resume of the same native session; it never changes the chat's selection. Success reports that the session runs and refreshes menus and panels showing it; failure reports a Russian reason with the fixed error code and correlation reference (never core's English text) and leaves the session `stopped` or `failed` as core persisted it. While core keeps a failure cause, `/status` and the session card show `Последняя ошибка: <причина> (<code>), <YYYY-MM-DD HH:mm UTC>`; it disappears once the session runs again. The card of a `failed` session offers **Восстановить** (unless `resume_unavailable`) and **Остановить…** and no longer suggests choosing another session.
- Persisted session rows are not sufficient to prove that a Pi process is live. While the supervisor is alive, core provides bounded native-session recovery and sends the fixed status events above; Telegram only presents these events and does not own retry policy. A graceful shutdown leaves session records stopped; Telegram restores chat selections on restart, but does not launch Pi until a new input or explicit `/resume`. After an unclean supervisor exit, saved rows may remain `running`; this milestone does not reattach or restart those processes, and a failed submit is explained without resending or creating a replacement.

## Incoming files and typing

- Authorized private-chat documents and photos are acknowledged immediately with `Получаю вложение…`, then downloaded through Telegram's `getFile` path with a 60-second total deadline and the 20,000,000-byte limit; photos use the highest-resolution available `PhotoSize`. Network download occurs outside the session inbox lock. Before saving/submitting, the transport reacquires the lock and revalidates the target/selection rule and lifecycle; a timeout explicitly says the file was not submitted and never retries automatically. Files are written with collision-resistant names and private permissions under `$HARNESSD_STATE_DIR/inbox/<SessionId>/`, and submitted with a local inbox path and optional caption as untrusted prompt text. Incoming bytes never enter the workspace or SQLite; if the per-session state-directory inbox destination would fall within the session's canonical workspace, the upload is rejected before creating or writing it. Photos are also passed transiently to Pi as image content. Each session inbox is limited to 100 MiB, with no limit on the number of files; a new upload removes the session's oldest harnessd-named inbox files, under the same lock, until it fits, so a running session never refuses an upload for lack of space. Files harnessd did not name are never removed; if they leave no room, nothing is removed and the save fails with the generic inbox error. An evicted file may still be referenced by an earlier prompt that Pi has not processed yet. Files expire seven days after receipt. Cleanup runs at startup and hourly, rechecks the lifecycle state under the per-session inbox lock shared with uploads/resume/submission, skips running sessions, and removes the inbox on stopped-session deletion; a stopped session's old inbox path is therefore not guaranteed to remain available beyond the TTL. Incomplete temporary files are removed; unsupported, missing-selection, oversized, download, and write failures receive fixed actionable replies without submitting partial content.
- While Pi reports an agent turn active, the transport refreshes the Telegram `typing` action for authorized chats currently selecting that session. It stops for chats on deselection and on turn settlement, error, or transport shutdown. If a chat reselects a session while its turn remains active, typing resumes for that chat.

## Non-goals and related contracts

Groups/channels, persistent event history, per-user session ownership, automatic input retries, Telegram-owned watchdog policy, recovery of stale running processes after an unclean supervisor exit, sandboxing, and secret-wallet behavior are not provided by this surface. CLI environment loading and user-level service management are defined by [CLI configuration](cli-configuration.md) and [user service](user-service.md). See [core session management](core-session-management.md) and [Pi RPC harness](pi-rpc-harness.md).
