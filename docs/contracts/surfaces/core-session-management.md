# Surface contract: core session management

## Boundary and ownership

The core owns stable supervisor-session identity, working-directory validation, session metadata and lifecycle decisions. It consumes harness/process functionality through adapter ports and does not import transport or harness implementations. The application runtime composes core with process, harness, and transport adapters; transports request core operations but do not own supervisor records, native Pi state, or lifecycle. A transport may persist its own routing choice (for example, Telegram's per-chat selected session) without changing core lifecycle policy. Runtime process selection defaults to trusted direct execution. Explicit isolated selection requires an injected provider declaring `process.isolation`, `process.launch`, and `process.signal`, and is checked before storage or transport startup. The runtime rejects caller-supplied harness arrays in isolated mode because it cannot guarantee they use the checked provider.

## Observable operations

- Create a session for a declared harness and existing local working directory; return its supervisor ID, optional human-readable name, and current state. Rename or clear the name without changing the stable supervisor ID, native Pi session, lifecycle, or `cwd`; duplicate names are valid.
- List and inspect sessions using supervisor IDs, independently of their workspace paths.
- Stop a session explicitly; an operator-requested stop is terminal and must not be restarted by automatic recovery. The adapter's `harness.stop` capability is checked independently; unsupported shutdown fails explicitly.
- Explicitly resume a deliberately stopped session, reusing its exact saved native session ID. Resume checks the declared and implemented `harness.resume` capability and does not use the automatic-recovery retry budget. Concurrent resume calls for one supervisor session share one launch; a running live session is returned idempotently. A non-stopped, missing-native-ID, or unsupported session fails explicitly; resume never falls back to fresh launch.
- Submit to a stopped session by first resuming that same native session, then submitting only the new input. Resume sends no prompt and old or uncertain input is never replayed. A failed resume leaves the record stopped where persistence permits and does not submit the new input.
- Delete a session record only after its persisted status is `stopped` and no live instance, launch, stop, or recovery operation still owns it. Deletion removes only the supervisor's SQLite metadata row; it does not remove Pi-native session files or the `cwd`. Active or otherwise non-stopped records fail explicitly and require `/stop` first. Successful deletion clears stale per-session terminal/event state, while the manager-lifetime recovery-attempt budget remains keyed by `SessionId` even if that ID is later reused.
- Close the manager during runtime shutdown: wait for in-flight launches, attempt to stop every live instance and join its event pump, retain all session records, and aggregate cleanup errors only after attempting all instances. Already terminal session records are unchanged.
- Submit input through core-owned, supervisor-ID-addressed routing to the matching harness instance. Inputs may carry transient image data for image-capable harnesses; image data is passed only to the live harness and is not persisted. Return the generated `InputId` only after the harness accepts the input. If delivery is uncertain, fail the submit without retry; the typed safe runtime error preserves the generated `InputId` when available.
- Cancel an accepted input by its `SessionId` and `InputId`, routed to the matching live harness instance after checking its declared `harness.cancel` capability. Unsupported cancellation fails explicitly; core never substitutes an adapter.
- Read ephemeral live harness status, model catalogs, and effort catalogs, and set a model or effort on the matching running instance. Model/effort operations check their independently declared capabilities and require a live instance; unsupported controls fail explicitly. A model change with optional effort is sequential; a confirmed model change followed by failed effort application is returned as an explicit partial result. These live values are not persisted.
- Reload Pi resources for an explicitly addressed running session through its declared `harness.reload` capability. Core serializes reload per session, rejects concurrent requests rather than queueing them, and excludes submissions/cancellation while reload owns the session. It revalidates live instance identity, running/attached lifecycle, stopping/recovery/terminal state, unsettled inputs, and the caller's selected-session identity immediately before adapter dispatch; adapter dispatch performs its own busy and lifecycle check. Reload does not resume, restart, replace, or create a process/session, and sends no model input.
- Subscribe to live `HarnessEvent` notifications from all running instances. Each event is tagged with the originating supervisor `SessionId`; per-session order is preserved and one observer failure cannot block the harness or other observers. The core does not await asynchronous observer work; synchronous observers must return promptly. Stopping a session terminates its event pump; events arriving during shutdown may not be forwarded.
- Core validates a session ID and canonical `cwd` before persisting a starting record or invoking a harness launcher. On successful launch it persists running status and optional native session ID; launch failure persists failed status. A stop concurrent with startup waits for startup/cleanup to settle, then shuts down the available instance and records terminal stopped status; startup cannot overwrite that stop. If recording a successful start fails and shutdown also fails, core retains the instance for an explicit stop retry and reports both errors.
- While the manager is alive, core watches the explicit `HarnessInstance.exit` promise; ordinary event-stream EOF is not treated as process death. On unexpected exit it drains that instance's event pump before publishing recovery status or starting a replacement.
- Automatic recovery is limited to three `resume` calls per `SessionId` for the manager lifetime, delayed by 250 ms, 1 s, and 4 s. The budget does not reset after a successful automatic recovery or ID reuse. Automatic and operator-initiated resume both require the declared and implemented `harness.resume` capability and the stored native session ID; they pass the exact supervisor ID, cwd, and native ID. Missing prerequisites or exhausted automatic recovery fails explicitly; core never falls back to a fresh launch.
- During automatic recovery, session status is persisted as `starting`, `running` on success, and `failed` on terminal failure. Operator-initiated resume likewise persists `starting` then `running`; if it fails, core restores `stopped` where persistence permits. Core emits fixed `harness_restarting`, `harness_recovered`, and `harness_recovery_failed` events scoped to the supervisor ID. If failure-status persistence itself fails, core still emits a safe recovery-failure event and does not imply that the failed status was stored.
- Core tracks unsettled `InputId`s in memory. After event draining, an unresolved input receives one `uncertain` event with its original ID; terminal uncertainty already reported by the harness is not duplicated. Recovery retains no prompt body and never resends old input; only a later explicit submit creates new work.
- Stop and manager close dominate automatic recovery and operator-initiated resume: pending backoff is cancelled, in-flight launches are joined, and any replacement racing with terminal intent is shut down before completion. Cleanup failures are reported and owned instances remain available for retry; terminal status is not written while a live instance remains owned.
- Session metadata is stored in SQLite under a supervisor-owned state directory, independent of `cwd`. Resolution order is explicit configured path, `HARNESSD_STATE_DIR`, `$XDG_STATE_HOME/harnessd`, then `~/.local/state/harnessd`; all configured paths must be fully qualified absolute paths (including a drive or valid UNC share on Windows), so the process working directory is never used to select state. On POSIX, the state directory must be owned by the current user and grant no group/other access; insecure existing directories are rejected, not silently changed.
- Resolve a requested `cwd` to its canonical path before starting any harness. Reject nonexistent, non-directory, or inaccessible paths without starting a harness. Any accessible existing directory is valid, including broad parent directories.

## Interfaces and compatibility

- Session, input, and adapter identities are stable opaque IDs; consumers must not infer identity from `cwd` or native harness IDs. `SessionSummary.name` is optional metadata stored with the supervisor record, normalized to one line, and limited to 64 Unicode code points. Harness events include output, status, error, input-delivery, and activity variants; fatal stream errors are explicitly marked. The ephemeral session-status result combines persisted session cwd/lifecycle data with optional live model, effort, aggregate usage, and authoritative adapter-provided context usage; absence of a live instance never adds these fields to session storage. Input-delivery events carry the existing `InputEvent` input ID, state, and optional detail; states are pending, accepted, completed, uncertain, or failed. Uncertainty does not establish whether Pi accepted the input; successful user cancellation is reported as failed with cancellation detail because core has no canceled state. Core forwards live events only; it does not persist an input/event history.
- Core ports declare capabilities. Adapters may provide fewer capabilities; calls to unsupported operations return an explicit error. Harness launch, stop, resume, input submission, and cancellation are checked independently.
- Harness-native session IDs are optional adapter-owned metadata, separate from supervisor IDs. Agent-originated file delivery is not a core session operation: the application runtime may pass an optional, session-scoped `AgentFileSendHandler` from a compatible transport to a harness; it does not persist file data or route through `SessionManager`.

## Failure, security, and limits

- Invalid paths, invalid session names, missing adapters, unsupported capabilities, duplicate/malformed IDs, non-stopped deletion, missing IDs, and persistence failures produce explicit errors. Reload failures (including selection change, busy/unavailable targets, and unconfirmed adapter completion) are typed safe outcomes; timeout or process loss does not imply success or trigger a retry. Invalid paths fail before launch; failed startup is not reported as running. An unexpected harness event-stream failure is surfaced as a generic session-scoped error event without exposing the underlying exception in the event; if it reaches the application request boundary, the runtime journals and returns a redacted, correlated traceback without changing core recovery behavior.
- State is never intentionally written under a selected workspace merely because it is the session `cwd`. POSIX state-directory ownership and mode are checked before opening SQLite; Windows ACLs are platform-managed and are not verified by core.
- Direct harness execution is trusted and runs with the supervisor user's operating-system permissions; `cwd` is not a sandbox or security boundary.
- Supervisor-managed credential values are not stored in session metadata or intentionally passed by core to harnesses. This does not guarantee that a same-user harness cannot read ambient credentials or write secret material into its workspace/output/network traffic.

## Non-goals

- Recovery after the supervisor process itself restarts, OS-level isolation/supervision, and secret-wallet operations are out of scope. Transport authentication/presentation and harness wire protocols are defined by their respective surfaces.
