# Surface contract: Telegram transport and CLI

## Boundary, consumers, and ownership

`TelegramTransportAdapter` in `src/telegram-transport.ts` implements the generic transport port. It owns Telegram parsing, sender/chat authorization, per-private-chat session selection and persistence, safe result/event presentation, long-polling lifecycle, and a token-derived polling lock. `src/cli.ts` validates configuration and composes one adapter with `ApplicationRuntime`; core and Pi RPC do not import Telegram code. Generic request/result/event guarantees are defined by [transport adapter](transport-adapter.md).

## Configuration and authorization

- Runtime startup loads an optional `.env` from the process current working directory before validating configuration. Process-environment values take precedence, file values are parsed as Node dotenv syntax (never executed as shell), and read errors are reported without exposing contents. See [CLI configuration](cli-configuration.md).
- `HARNESSD_TELEGRAM_BOT_TOKEN` and a nonempty comma-separated `HARNESSD_TELEGRAM_ALLOWED_USER_IDS` are required. IDs must be positive safe integers. `HARNESSD_PI_EXECUTABLE` defaults to `pi`; `HARNESSD_STATE_DIR` uses the core's standard resolution; `HARNESSD_HOME` optionally selects the initial per-chat directory and `/new` default; it defaults to `/` and is not a filesystem boundary. `harnessd --help` reports usage without requiring or loading configuration.
- `HARNESSD_EXECUTION_MODE` defaults to `direct` (trusted; `cwd` is not a sandbox). The CLI accepts only `direct` or `isolated`; because it registers no isolation provider, an isolated request fails safely before transport startup. Invalid values are rejected before configuration-driven transport construction.
- Every Telegram update, including callback queries, passes middleware before handlers: the sender must exist, have a positive safe numeric ID in the allowlist, and the chat must be `private`. Unauthorized/missing/malformed senders and groups/channels receive no reply, session data, or core dispatch.
- Allowlisted operators share access to all local sessions. The bot token is not logged or passed to Pi; child environment behavior remains the process-provider contract. Direct Pi is trusted local execution with the supervisor user's OS permissions; `cwd` is not a sandbox.

## Commands and session routing

- Supported commands: `/help`, `/menu`, `/rename [sessionId] <name|--clear>`, `/sessions`, `/new [cwd]`, `/ls [path]`, `/cd [path]`, `/send <path>`, `/use [sessionId]`, `/resume [sessionId]`, `/inspect [sessionId]`, `/status`, `/model [provider/modelId [effort]]`, `/effort [level]`, `/stop [sessionId]`, `/delete <sessionId>`, and `/cancel <inputId>`. If `/use` has no ID, it confirms the remembered selection or explains how to choose one; missing-selection replies link to `/sessions` and `/menu`. The shared visibility-tagged catalog generates CLI help, Telegram `/help`, and Telegram's command menu. Registration is best-effort; failure emits a correlated redacted diagnostic but does not prevent polling or manual command handling. Plain text and media submit to the session selected by that private chat; if it is deliberately stopped, core resumes that exact saved Pi-native session before submitting only the new input once. After a graceful service restart, the transport restores each chat's saved selection without starting Pi at transport startup; the first new input triggers core's normal resume path. If Pi is already working, the Pi RPC harness submits the new input to Pi's native steering queue rather than rejecting it or holding a second harnessd queue. `/resume` does not change selection and never falls back to a new session. `/model` and `/effort` list available/current controls for the selected live session; model IDs are selected by stable `provider/modelId`, never by display name.
- `/new` treats the entire remaining command text as one `cwd` path; paths with spaces work unquoted, and one matching pair of outer single or double quotes is stripped. Unmatched leading quotes receive a safe syntax hint. It performs no shell execution or expansion other than `~` and `~/...` to the operating-system user's home. Without a path, `/new` uses that chat's current directory, initially `HARNESSD_HOME` or `/`; explicit relative paths resolve from the same chat directory, and absolute paths are accepted. `~` expansion is independent of `HARNESSD_HOME`. Core canonicalizes and validates either path. `/use` inspects before selection, and a failed lookup leaves the existing selection unchanged. Selection changes from `/use`, `/new`, and `/menu` are persisted per authorized private chat; bare `/use` inspects and confirms that saved selection. Explicit stop clears the selected chat's saved choice, and successful deletion clears every chat selecting the deleted session. Missing-session and persistence failures are reported with actionable guidance. Inspect/stop default to the selected session; cancel requires a selected session and exact `InputId`. Successful `/stop` clears that chat's selection when it stopped the currently selected session, so the operator must `/use` that session before unqualified `/resume` or text-driven auto-resume.
- `/ls [path]` lists immediate files and folders in the supplied or current chat directory, hides dotfiles by default, bounds output to 100 entries, and never reads file contents. `/cd [path]` changes only the current chat's volatile navigation directory; `/cd` without a path goes to the OS user's home. Relative paths use the chat directory and absolute paths, `..`, and symlinks can reach any directory accessible to the service OS user. `HARNESSD_HOME` only selects the initial directory; it is not a sandbox. `/cd` does not change the cwd of running sessions. `/send <path>` uploads a regular file from the selected session's canonical cwd to that authorized private chat only; relative paths resolve against the session cwd, paths outside it are rejected, and files over 20 MiB or non-regular files fail safely. The Pi `send_file` tool explicitly sends a regular workspace file (optionally with a caption) to authorized private chats currently selecting that session; it uses the same canonical-workspace, symlink, regular-file, and 20 MiB checks. Outer matching quotes may surround a path containing spaces.
- Session names are optional, shared metadata in the harnessd SQLite record, independent of Pi-native data and `cwd`. They are trimmed, single-line, nonempty when set, and limited to 64 Unicode code points; duplicates are allowed. `/rename [sessionId] <name>` targets the explicit ID or selected session, and `--clear` removes the name. `/sessions` and `/inspect` render `Name · #<full SessionId>` (or `#<full SessionId>`) in plain searchable text while escaping HTML and abbreviating displayed cwd paths after 600 Unicode code points. `/delete` requires one explicit ID and removes only a stopped harnessd metadata row; it neither stops a live session nor deletes Pi-native files or its `cwd`. A non-stopped record returns guidance to `/stop` it first. Successful deletion clears volatile selections for that ID and removes its inbox; if filesystem cleanup fails, deletion remains successful and the transport reports cleanup as pending for a later sweep. `/status` reports saved cwd/lifecycle plus live model, effort, aggregate usage, and estimated USD cost; missing live data is marked unavailable, cost is not provider billing, and optional plugin-only per-model/subagent details are excluded. A partially successful model change is reported without claiming rollback.

## Session panel, event presentation, and backpressure

- `/menu` creates or refreshes one pinned inline panel per authorized private chat. It shows the current selected session first and live parent-session usage when available (`↑` input, `↓` output, `R` cache reads, `CH` cache-hit rate, estimated cost, and actual context occupancy from Pi RPC `contextUsage`). Missing or null values display as unavailable, never as zero; subagent metrics are not available through supported harness interfaces. Previous/next browse the deterministic `/sessions` order; the center **Выбрать** action alone commits the preview as the chat's selected session. Preview and folder navigation are volatile. The bot-token-scoped private state file stores panel message IDs and per-chat selected session IDs (never prompt bodies); version-1 panel files remain readable and are upgraded on the next write.
- Inline panel routes include session list/details, folder navigation, new-session creation with an optional name, model/effort selection, and stop/delete actions with button-level confirmation. The same core operations and safety checks as slash commands apply. Unauthorized and non-private callbacks are rejected before core dispatch. Malformed session IDs and callbacks targeting a session absent from the transport's current in-memory session set are also rejected before dispatch; stale session buttons offer a `/menu` refresh. Name prompts use ForceReply; only replies to an active prompt are consumed as names, and stale replies are not submitted to Pi. A transient/uncertain panel-edit failure is not retried by sending a duplicate message; an explicit “message to edit not found” response permits creating a replacement panel. Pin failure leaves `/menu` and slash commands available and reports that the panel is unpinned.
- Completed assistant output is buffered as a whole turn. The body is followed by a blank line and a searchable `Name · <full SessionId>` footer (or only `<full SessionId>` when unnamed); the full session ID is rendered in monospace with a Telegram code entity and no `#` tag. For each Telegram-triggered turn, one reply activity bubble is edited in place to show Pi input state, bounded tool summaries/outcomes, notifications, and available model/effort/usage/context values; it is deleted only after the separately delivered final answer and session settlement. RPC prompt acceptance is not presented as proof that a queued input has started; run settlement is session-scoped. Routine `agent_start`, `agent_end`, and `agent_settled` lifecycle fragments are not emitted separately. Safe detailed errors, harness recovery statuses, and input-delivery notifications remain visible and session-correlated; identical errors are deduplicated until recovery. Event bodies remain literal plain text; only the session ID footer entity is formatted, so HTML-like output is not interpreted. Raw reasoning and stderr are never echoed. A submit diagnostic may include its exactly correlated input text in the private chat, but prompt contents are never logged or persisted. Model/workspace output is not universally redacted and may contain sensitive workspace data.
- If a whole turn exceeds Telegram's 4096-character limit, it is split into ordered parts. Each part fits within the limit, repeats the monospace session-ID footer, and includes its `i/N` marker; chunk boundaries preserve Unicode surrogate pairs and content is not resent. Overflow remains bounded and is reported explicitly.
- Runtime operation failures include an actionable safe summary plus exception type, stack, and nested causes when safe; their journal entry carries the operation kind and a short correlation reference. Pi startup/control wrappers intentionally omit raw Pi provider causes and stderr, while preserving the typed failure and harnessd stack. Telegram sends error replies as escaped HTML `<pre><code>` blocks, bounded below Telegram's 4096-character limit; exception text is treated as literal text, never markup. Known Telegram update and callback failures include a correlation reference and traceback. Diagnostics redact the configured bot token, token-shaped strings, and common credential assignments. Submitted prompt text is excluded from logs and persistent state; it may appear only in the private, exactly correlated submit-error reply. Paths may appear in diagnostics. A failure to send a diagnostic is best-effort and does not change operation semantics.
- Successful text, photo, and document submissions show the `InputId` state in the editable activity bubble and add an `👀` reaction to the originating Telegram message after Pi confirms acceptance (including queued acceptance). The reaction means accepted by Pi, not completed. If Telegram cannot set the reaction, harnessd logs a safe diagnostic; the activity bubble still provides the acknowledgment. Rejected or uncertain submissions are not reacted as accepted. Event messages are queued per chat in session-event order. Before sending, each item rechecks that the chat still selects that session. The successful submit result supplies the single `InputId` acceptance confirmation; the subsequent `accepted` event is not echoed as a duplicate. Repeated states for one input may be coalesced only at the newest event position, preserving the relative order of retained output/status/input notifications. Identical generic error events are shown once per failure episode and become visible again after `harness_recovered`.
- Each chat has a bounded queue (32,768 pending characters, bounded message/control counts) and each API send has a 5-second deadline. Excess output is discarded with a safe omission notice; input-delivery control items receive reserved capacity and output is evicted first. If a chat's event send times out/fails, that chat's event queue is disabled for the remainder of the service run; other recipients and core event delivery continue. Direct command replies are best-effort and time-bounded too.
- Submit uncertainty is reported with the original `InputId` in the safe correlated error result and/or event notification. No automatic resend occurs. New operator inputs may still be submitted to Pi's native queue after an uncertain delivery; the uncertain input itself is never resent. While multiple inputs are outstanding, `/cancel <inputId>` is refused with an explanation because Pi RPC cannot cancel one queued item without aborting the run; no run or queued input is canceled. A new message arriving during a single-input cancellation is submitted to Pi after the abort response, preventing the run-wide abort from discarding it. If cancellation's response is uncertain, the message waits until Pi settles or exits before submission. An overflowed notification cannot cause an uncertain input to be resent.

## Polling lifecycle and failure behavior

- CLI startup initializes grammY with an abort signal before beginning long polling. A startup signal aborts initialization and runtime startup rolls back. After readiness, an unexpected fatal polling exit requests safe runtime shutdown; the CLI does not silently leave a non-polling runtime active.
- A SHA-256-derived, non-secret lock filename is created exclusively under the supervisor state directory. Its mode is `0600` and its content is only the owner PID. A second harnessd process sharing that state directory is rejected. A stale owner is removed only when the PID is demonstrably absent; ambiguous or unrecoverable lock/recovery state fails closed.
- `SIGINT`/`SIGTERM` stop the runtime. Polling stop, initialization, and notification shutdown are awaited within bounded deadlines. The lock is released only after polling termination is confirmed; incomplete cleanup retains ownership rather than allowing a second poller. Telegram API conflicts with an unrelated poller are treated as fatal; this local lock does not prevent another program from using the same bot token.
- Persisted session rows are not sufficient to prove that a Pi process is live. While the supervisor is alive, core provides bounded native-session recovery and sends the fixed status events above; Telegram only presents these events and does not own retry policy. A graceful shutdown leaves session records stopped; Telegram restores chat selections on restart, but does not launch Pi until a new input or explicit `/resume`. After an unclean supervisor exit, saved rows may remain `running`; this milestone does not reattach or restart those processes, and a failed submit is explained without resending or creating a replacement.

## Incoming files and typing

- Authorized private-chat documents and photos are downloaded through Telegram's `getFile` path with the 20,000,000-byte limit; photos use the highest-resolution available `PhotoSize`. Files are written with collision-resistant names and private permissions under `$HARNESSD_STATE_DIR/inbox/<SessionId>/`, and submitted with a local inbox path and optional caption as untrusted prompt text. Incoming bytes never enter the workspace or SQLite; if the per-session state-directory inbox destination would fall within the session's canonical workspace, the upload is rejected before creating or writing it. Photos are also passed transiently to Pi as image content. Each session inbox is limited to 10 files and 100 MiB; over-quota uploads are rejected without evicting retained files. Files expire seven days after receipt. Cleanup runs at startup and hourly, rechecks the lifecycle state under the per-session inbox lock shared with uploads/resume/submission, skips running sessions, and removes the inbox on stopped-session deletion; a stopped session's old inbox path is therefore not guaranteed to remain available beyond the TTL. Incomplete temporary files are removed; unsupported, missing-selection, oversized, quota, download, and write failures receive fixed actionable replies without submitting partial content.
- While Pi reports an agent turn active, the transport refreshes the Telegram `typing` action for authorized chats currently selecting that session. It stops for chats on deselection and on turn settlement, error, or transport shutdown. If a chat reselects a session while its turn remains active, typing resumes for that chat.

## Non-goals and related contracts

Groups/channels, persistent event history, per-user session ownership, automatic input retries, Telegram-owned watchdog policy, recovery of stale running processes after an unclean supervisor exit, sandboxing, and secret-wallet behavior are not provided by this surface. CLI environment loading and user-level service management are defined by [CLI configuration](cli-configuration.md) and [user service](user-service.md). See [core session management](core-session-management.md) and [Pi RPC harness](pi-rpc-harness.md).
