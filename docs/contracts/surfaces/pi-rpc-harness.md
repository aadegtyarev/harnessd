# Surface contract: Pi RPC harness

## Boundary and ownership

`PiRpcHarnessAdapter` in `src/harness/` owns Pi RPC process arguments, JSONL framing, command correlation, event decoding, prompt delivery, cancellation, and bounded shutdown. It consumes the generic `ProcessProvider`; Pi protocol details do not enter the process-provider port. It advertises launch, stop, resume, cancel, input-submit, session-status, model-list/model-set, and effort-list/effort-set capabilities; `harness.file.send` is advertised only when an agent file-send handler is configured. `SessionManager` routes input cancellation and forwards live harness events. The application runtime composes it with the process provider and configured transports. `PiRpcHarnessAdapter` consumes only the generic process port and does not infer isolation; runtime selection determines which provider is passed to the default Pi harness. `src/cli.ts` composes the runtime with the Telegram transport; see [Telegram transport](telegram-transport.md) for external commands and presentation.

## Observable behavior

- Launches one Pi CLI process per instance with `--mode rpc`, pipe stdio, configured cwd, and optional replacement environment. An executable regular file with the exact `#!/usr/bin/env node` shebang is launched as `process.execPath <script> ...`; an executable basename is inspected through the configured replacement `PATH`, or `/usr/bin:/bin` on POSIX when the replacement environment omits `PATH`. This does not add or inherit child environment values. Native executables and other shebangs are left unchanged. The process provider must declare `process.launch` and `process.signal`; missing pipe streams fail launch.
- Readiness requires correlated `get_state` within the configured startup bound. The exact returned `data.sessionId` is exposed as `nativeSessionId`. Resume requires a native ID, passes it exactly as `--session <id>`, and rejects if readiness returns a different ID; the adapter never uses `--session-id`. Adapter-controlled session/mode flags, including `--no-session`, `--continue`/`-c`, `--resume`/`-r`, and `--fork`, cannot be overridden in configured args.
- Sends text-only input through Pi RPC `prompt` with `{ message }`; image-bearing input adds Pi's `images` array and remains transient. If a run or another prompt is already active/pending, `prompt` includes `streamingBehavior: "steer"` so Pi's own queue accepts the additional input. Each prompt retains a separate `InputId`; successful RPC acknowledgement emits accepted, final `agent_settled` completes every acknowledged outstanding input (Pi does not identify individual queued items in that event), and a successful `handled` disposition completes immediately. Definite rejection emits failed; a lost response or process exit emits uncertain. No input is automatically retried. After uncertainty, later operator input may still be submitted to Pi, but the uncertain input itself is never resent. A timeout after prompt write throws `UncertainInputDeliveryError` carrying `InputId` without prompt content; the application runtime preserves that ID in the typed safe submit error.
- Exposes instance-scoped live control through `HarnessInstance`: current state and aggregate usage use `get_state` and `get_session_stats`; model and thinking-level catalogs use `get_available_models` and `get_available_thinking_levels`; selections use `set_model` with exact provider/model ID and `set_thinking_level`. A requested model/effort is checked against the corresponding available catalog before selection. The status result retains only model identity/name, thinking level, aggregate token counts, numeric USD cost, and Pi's `contextUsage.tokens`, `contextUsage.contextWindow`, and `contextUsage.percent`. Null/absent context values remain unknown and are never derived from aggregate totals. It does not expose `sessionFile`, transcripts, or detailed per-model/subagent usage. No control values are persisted by the harness.
- When configured with an agent file-send handler, each Pi instance receives a fresh random bearer token and a loopback-only HTTP bridge bound to `127.0.0.1`, plus the bundled `send_file` extension. The tool accepts a workspace path and optional caption; the session-scoped transport handler owns workspace/regular-file/size checks and recipient delivery. The bridge bounds and validates request data, does not expose handler errors, and closes on process exit or harness shutdown. No bridge is created when file sending is unavailable.
- Text deltas produce output events; agent lifecycle produces status events. Thinking start/end, tool execution start/end, and safe extension notifications produce bounded activity events; tool summaries include only selected call arguments (never tool output or raw reasoning). `extension_error` and unsupported/cancelled dialog requests produce detailed, credential-redacted session errors. `notify`, `setStatus`, and `setWidget` are status/activity notifications rather than session errors; `setTitle` is ignored. Dialog extension UI requests are answered with `cancelled: true` where a response ID exists. A correlated response must contain a string ID/command and boolean success; malformed acknowledgements fail the protocol and leave prompt delivery uncertain.
- RPC stdout is strict LF-delimited JSONL; CRLF is accepted. UTF-8 chunk boundaries are handled; U+2028/U+2029 do not delimit records. Oversized or malformed records fail explicitly and trigger bounded process cleanup. Process exit does not finalize events until stdout reaches EOF, allowing final records and acknowledgements to drain; a bounded exit-drain timeout makes missing EOF explicit. Stderr is continuously drained and neither logged nor retained. Unsupported extension UI requests emit an actionable detail where available; supported dialog requests are cancelled with a matching response so Pi does not stall.
- Each `HarnessInstance` exposes the managed process exit code/signal separately from RPC event-stream EOF. `SessionManager`, not this adapter, observes that signal, drains the old event pump, and owns bounded in-process native-session recovery as well as operator-initiated resume of stopped sessions. Both use the exact saved native ID; resume readiness must report the same native Pi session ID.
- Shutdown closes stdin, waits a bounded interval, then drains stdout to EOF before finalizing; TERM and KILL waits are bounded. Protocol/process failure also initiates bounded child cleanup; shutdown remains idempotent.

## Errors, privacy, and limitations

Startup, command, protocol, process, and shutdown failures reject or emit explicit events. Known Pi launch failures are represented by fixed startup error codes for missing/inaccessible executables, early process exit, readiness timeout, and other startup failures; the application runtime maps these to actionable user-facing messages and journals a correlated harnessd stack. Control RPC failures use safe fixed codes; stderr is never exposed. Structured extension failures are the exception: their useful event/error detail is credential-redacted before forwarding to authorized transports. Harnessd wrapper stacks may be shown; submitted prompts are excluded from logs and persistent diagnostics. Timeout values must be positive integers no greater than Node's timer maximum (2,147,483,647 ms); record-size limit must be from 1 byte through 64 MiB. Diagnostic text does not contain prompt contents or stderr. Cancellation uses RPC `abort`; `agent_settled` may arrive before the abort response, so delivery is held until that response: successful abort reports failed with canceled detail, rejected abort reports completion if already settled, and lost abort response reports uncertain. Abort replies are bound to their originating `InputId`. Because Pi's abort is run-wide rather than queue-item-specific, harnessd refuses cancellation while multiple inputs are outstanding and does not abort or clear queued work; the error explains this limitation. A submission arriving during a single-input abort waits for its response before writing a prompt, preventing that abort from affecting newly accepted input. If the abort response is lost while the run is still active, queued submissions remain gated until `agent_settled` or process exit; no new prompt is sent into an operation with uncertain cancellation outcome. Core has no cancelled state. The adapter performs no recovery or input retry; `SessionManager` provides bounded recovery only while the supervisor remains alive. Reattachment after supervisor restart, extension UI forwarding, and delivery retry are not provided.
