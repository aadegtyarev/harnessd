# Surface contract: Pi RPC harness

## Boundary and ownership

`PiRpcHarnessAdapter` in `src/harness/` owns Pi RPC process arguments, JSONL framing, command correlation, event decoding, prompt delivery, cancellation, and bounded shutdown. It consumes the generic `ProcessProvider`; Pi protocol details do not enter the process-provider port. It advertises launch, stop, resume, cancel, input-submit, session-status, model-list/model-set, and effort-list/effort-set capabilities; `harness.file.send` is advertised only when an agent file-send handler is configured. `SessionManager` routes input cancellation and forwards live harness events. The application runtime composes it with the process provider and configured transports. `PiRpcHarnessAdapter` consumes only the generic process port and does not infer isolation; runtime selection determines which provider is passed to the default Pi harness. `src/cli.ts` composes the runtime with the Telegram transport; see [Telegram transport](telegram-transport.md) for external commands and presentation.

## Observable behavior

- Launches one Pi CLI process per instance with `--mode rpc`, pipe stdio, configured cwd, and optional replacement environment. An executable regular file with the exact `#!/usr/bin/env node` shebang is launched as `process.execPath <script> ...`; an executable basename is inspected through the configured replacement `PATH`, or `/usr/bin:/bin` on POSIX when the replacement environment omits `PATH`. This does not add or inherit child environment values. Native executables and other shebangs are left unchanged. The process provider must declare `process.launch` and `process.signal`; missing pipe streams fail launch.
- Readiness requires correlated `get_state` within the configured startup bound. The exact returned `data.sessionId` is exposed as `nativeSessionId`. Resume requires a native ID, passes it exactly as `--session <id>`, and rejects if readiness returns a different ID; the adapter never uses `--session-id`. Adapter-controlled session/mode flags, including `--no-session`, `--continue`/`-c`, `--resume`/`-r`, and `--fork`, cannot be overridden in configured args.
- Every launch and resume injects a Pi extension with a per-instance random internal reload command name. Before the instance is usable, correlated `get_commands` readiness must report exactly one extension command matching that name and its fixed description; otherwise startup fails. The extension remains loaded after reload and can be used repeatedly.
- Sends text-only input through Pi RPC `prompt` with `{ message }`; image-bearing input adds Pi's `images` array and remains transient. If a run or another prompt is already active/pending, `prompt` includes `streamingBehavior: "steer"` so Pi's own queue accepts the additional input. Each prompt retains a separate `InputId`; its pending event is emitted after any abort gate opens and before the prompt command is written. Event publication preserves that lifecycle order: successful RPC acknowledgement emits accepted, and a successful `handled` disposition completes immediately. A final `agent_settled` normally completes acknowledged outstanding inputs, but when it settles a current-run cancellation it completes only the canceled run's input; preserved steered/queued inputs remain unresolved until a later run settlement confirms their consumption (Pi does not identify individual queued items in the event). Definite rejection emits failed; a lost response or process exit emits uncertain, meaning Pi may have accepted the input but its acknowledgement was lost. The adapter does not make a false delivery claim, and no input is automatically retried. After uncertainty, later operator input may still be submitted to Pi, but the uncertain input itself is never resent. A timeout after prompt write throws `UncertainInputDeliveryError` carrying `InputId` without prompt content; the application runtime preserves that ID in the typed safe submit error.
- Exposes instance-scoped live control through `HarnessInstance`: current state and aggregate usage use `get_state` and `get_session_stats`; model and thinking-level catalogs use `get_available_models` and `get_available_thinking_levels`; selections use `set_model` with exact provider/model ID and `set_thinking_level`. A requested model/effort is checked against the corresponding available catalog before selection. The status result retains only model identity/name, thinking level, aggregate token counts, numeric USD cost, and Pi's `contextUsage.tokens`, `contextUsage.contextWindow`, and `contextUsage.percent`. Null/absent context values remain unknown and are never derived from aggregate totals. It does not expose `sessionFile`, transcripts, or detailed per-model/subagent usage. No control values are persisted by the harness.
- Command inventory is populated at readiness/resume and refreshed on each list/run request; reload refreshes it after confirmed success. A discovery failure is explicit (`COMMAND_DISCOVERY_FAILED`), and a post-reload refresh failure clears the cached inventory so callers cannot use stale commands. Only valid entries whose Pi `source` is `extension` are exposed; prompt templates, skills, native commands, the per-instance internal reload command, duplicates, and malformed entries are excluded. Neither `sourceInfo` nor its paths are retained in `HarnessCommand`. Dynamic commands are sent through RPC `prompt` as `/{name}{exactRawRemainder}`. Each run request discovers and validates fresh inventory before enqueueing its prompt; inventory is not revalidated at the actual serialized write boundary. After any abort gate, that boundary synchronously checks the typed caller guard and current selection, lifecycle, process, reload, abort, and cancellation state. Queued commands whose timeout expires before write are cancelled and skipped. Command dispatch rejects while reload owns the instance, waits behind cancellation, but is allowed while Pi is ordinarily busy. A successful `handled` disposition remains `handled`; successful `started`, `queued`, or `accepted` dispositions normalize to `accepted`. A successful unknown disposition is unconfirmed/uncertain, not a definite rejection. The Pi prompt response carries disposition only. `/cost` result text is instead returned as a `message_start` custom message with role `custom`, custom type `pi-ad-session-usage:report`, and string content; the adapter subscribes before dispatch, serializes to one outstanding request, requires a matching report plus `handled` disposition within a bounded deadline, and returns only the sanitized bounded content. Missing, malformed, or late reports fail safely; timeout quarantines further cost requests for that instance so a late report cannot correlate to a later request. No command is replayed. A queued prompt acknowledgment means Pi accepted work behind a busy run, not that the model consumed it; busy/background-wait states such as `bg_wait` remain queued until model activity is observed.
- Reload sends exactly one RPC `prompt` containing only the injected internal command, never an operator/model prompt. It is permitted only while the instance is idle and synchronously rechecks process/event liveness, active inputs, compaction, abort, and core's dispatch callback at the actual serialized write boundary. Only a correlated successful response with disposition `handled` and no correlated extension error is success. Extension lifecycle errors are suppressed from generic session-event presentation and make reload fail safely. A timeout/cancellation before write is a definite pre-dispatch failure and releases ownership; after write begins, timeout or process exit is unconfirmed, retains reload ownership until the response/exit resolves uncertainty, and never causes retry. On confirmed success the extension inventory is refreshed; if that refresh fails it is cleared rather than left stale. Reload does not restart Pi or create model/input side effects.
- When configured with an agent file-send handler, each Pi instance receives a fresh random bearer token and a loopback-only HTTP bridge bound to `127.0.0.1`, plus the bundled `send_file` extension. The tool accepts a workspace path and optional caption; the session-scoped transport handler owns workspace/regular-file/size checks and recipient delivery. The bridge bounds and validates request data, does not expose handler errors, and closes on process exit or harness shutdown. No bridge is created when file sending is unavailable.
- Text deltas produce output events; agent lifecycle produces status events. A completed assistant `message_end` produces a `message_end` status event (user/tool messages do not), so transports can deliver each answer before the run settles. Thinking start/end, tool execution start/end, and safe extension notifications produce bounded activity events; tool summaries include only selected call arguments (never tool output). A completed thinking block yields one `thought` event: its last bold reasoning-summary title, otherwise its first sentence, redacted and clipped (≤160/120 characters); full reasoning is never forwarded. A bash `tool_end` carries `detail` with the exit code parsed from the result (`exit N`, `exit 0`, or `error`). An `entry_appended` Pi /task entry (`pi-ad-hooks-task`) yields a `task` event (goal, progress, status, step, limit). `bg_wait` and `subagent` coordination actions get plain-language Russian summaries. A `message_end` for a `custom` message of type `subagent-notify` yields an `agent_notice` activity event with the notice text, redacted and clipped to 4000 characters. `setWidget` notifications carry `widgetKey`; a keyed widget with no lines is forwarded as an empty notification so transports can drop what it showed. `extension_error` and unsupported/cancelled dialog requests produce detailed, credential-redacted session errors. `notify`, `setStatus`, and `setWidget` are status/activity notifications rather than session errors; `setTitle` is ignored. Dialog extension UI requests are answered with `cancelled: true` where a response ID exists. A correlated response must contain a string ID/command and boolean success; malformed acknowledgements fail the protocol and leave prompt delivery uncertain.
- RPC stdout is strict LF-delimited JSONL; CRLF is accepted. UTF-8 chunk boundaries are handled; U+2028/U+2029 do not delimit records. Oversized or malformed records fail explicitly and trigger bounded process cleanup. Process exit does not finalize events until stdout reaches EOF, allowing final records and acknowledgements to drain; a bounded exit-drain timeout makes missing EOF explicit. Stderr is continuously drained; each instance keeps only a bounded (2,048-character), credential-redacted tail, exposed through `HarnessInstance.diagnosticTail()` and, when readiness fails, as a non-enumerable `diagnosticTail` on the rejected startup error. Core uses it only in its `harnessd:` failure journal lines; it is never forwarded in events, sent to transports, or persisted. Unsupported extension UI requests emit an actionable detail where available; supported dialog requests are cancelled with a matching response so Pi does not stall.
- Each `HarnessInstance` exposes the managed process exit code/signal separately from RPC event-stream EOF. `SessionManager`, not this adapter, observes that signal, drains the old event pump, and owns bounded in-process native-session recovery as well as operator-initiated resume of stopped sessions. Both use the exact saved native ID; resume readiness must report the same native Pi session ID.
- Shutdown closes stdin, waits a bounded interval, then drains stdout to EOF before finalizing; TERM and KILL waits are bounded. Protocol/process failure also initiates bounded child cleanup; shutdown remains idempotent.

## Errors, privacy, and limitations

Startup, command, protocol, process, and shutdown failures reject or emit explicit events. Known Pi launch failures are represented by fixed startup error codes for missing/inaccessible executables, early process exit, readiness timeout, and other startup failures; the application runtime maps these to actionable user-facing messages and journals a correlated harnessd stack. Control RPC failures use safe fixed codes; stderr is never exposed to transports or persisted. Structured extension failures are the exception: their useful event/error detail is credential-redacted before forwarding to authorized transports. Harnessd wrapper stacks may be shown; submitted prompts are excluded from logs and persistent diagnostics. Timeout values must be positive integers no greater than Node's timer maximum (2,147,483,647 ms); record-size limit must be from 1 byte through 64 MiB. Transport-facing diagnostic text does not contain prompt contents or stderr. Cancellation uses RPC `abort`; `agent_settled` may arrive before the abort response, so delivery is held until that response: successful abort reports failed with canceled detail, rejected abort reports completion if already settled, and lost abort response reports uncertain. Abort replies are bound to their originating `InputId`. Exact-ID cancellation remains refused while multiple inputs are outstanding because Pi's abort is run-wide. A separate current-active-run cancellation selects the unique acknowledged non-steered active input, aborts that run even when Pi-native queued inputs exist, and leaves queued inputs in Pi's native queue; it neither clears nor resubmits them. If active input identity is unavailable or ambiguous, current-run cancellation fails safely. A submission arriving during a single-input abort waits for its response before writing a prompt, preventing that abort from affecting newly accepted input. If the abort response is lost while the run is still active, queued submissions remain gated until `agent_settled` or process exit; no new prompt is sent into an operation with uncertain cancellation outcome. Core has no cancelled state. The adapter performs no recovery or input retry; `SessionManager` provides bounded recovery only while the supervisor remains alive. Reattachment after supervisor restart, extension UI forwarding, and delivery retry are not provided. Deterministic Pi 1.0.4-shaped protocol tests cover reload identity, dispatch, races, lifecycle errors, and repeated acknowledgements. An isolated live Pi 1.0.4 smoke for launch → reload → second reload → resume exited with `PI_EXITED_BEFORE_READY` before any model/provider call. Actual extension survival across live launch/resume/repeated reload therefore remains unverified; this is an explicitly accepted, non-blocking validation limitation, not a passed scenario.
